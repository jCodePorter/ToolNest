## Cron 预览列表「等待时长」语义修复

**起因**：用户截图 `0 0 * * *` 的「未来执行时间」列表，红框圈出 `(+1 天)` 一列，反馈「不对」。
核对后确认日期/星期（09-28 周一 … 10-07 周三）、序号对齐、字段说明**全部正确**，
问题只在标注语义：原实现是「与上一次的间隔」，对「每天零点」这种固定周期每行都是无差别的 `+1 天`。
经确认，目标语义改为**距当前时刻还有多久**（逐行递增）。

**改动**

- `modules/cron/CronModule.java`
  - 新增 `public static String buildNextText(List<LocalDateTime>, LocalDateTime now)`：
    渲染整份列表文本（序号 + 时间 + 星期 + 距 now 的等待时长），**第一行也带标注**。
    抽成静态方法是为了能被探针直接断言 —— 界面只剩薄壳。
  - 新增 `public static String humanDuration(Duration)`：秒/分钟/小时/天 四级，最多两级组合
    （`30 秒` / `1 分钟 30 秒` / `5 分钟` / `2 小时` / `1 天 6 小时`）。
    顺带修掉一个潜在 bug：旧版用 `Duration.toMinutes()` 取整，6 段表达式（每 30 秒）
    会显示成 `+0 分钟`。
  - 删除死代码 `FMT_WEEK` 与旧 `intervalText(long)`。
- `README.md`：执行预览一节改为「距离当前时刻还有多久」，并给出 `+6 小时 3 分` / `+30 秒` 的例子。
- `verify/CronTest.java`：新增 12 条断言（6 条文案 + 4 条列表渲染 + 2 条秒级），
  探针计数 **31 → 43**。

**踩到的坑（值得记住）**

> **`*/` 写在 Javadoc/块注释里会提前闭合注释**。我在 `humanDuration` 的 Javadoc 里写了
> `{@code */30 * * * * *}`，`*/` 直接结束了注释块，编译报出一堆
> 「非法字符: '\uff09'」「未命名类不应有程序包声明」—— 报错位置在注释之后几十行，
> 很容易误判成括号不匹配。`CronExpression` 里早已用 `{@code *}{@code /15}` 拆分规避。
> 修法：注释里别出现 `*/`，或拆成 `{@code *}{@code /30}`。

**验证**

- `verify.cmd cron` → **43 passed / 0 failed**（新增断言后做了反向验证：
  把逻辑退回旧行为，**5 条断言变红**，确认断言不是摆设）
- 新增**界面级探针 `CronModuleProbe`**（`verify.cmd cronui`，已注册进 verify.cmd）：
  驱动真实模块 → 把表达式填成 `0 0 * * *` → 读真实 TextArea 文本 →
  断言「10 行都带标注 + 各行等待时长互不相同」，并截图到 `target/cron-probe/`。
  实测渲染：
  ```
   1. 2026-09-28 00:00:00  周一   (+5 小时 52 分)
   2. 2026-09-29 00:00:00  周二   (+1 天 5 小时)
   ...
  10. 2026-10-07 00:00:00  周三   (+9 天 5 小时)
  ```
  → **6 passed / 0 failed**
- `verify.cmd smoke -nobuild` → **21 passed / 0 failed**，CSS 错误 **0**；
  `target/smoke/cron.png` 目视确认 `0 9 * * 1-5` 渲染为
  `+14 小时 54 分` / `+1 天 14 小时` / `+2 天 14 小时` … 逐行递增，且正确跳过周末（10-02 周五 → 10-05 周一 +7 天）。
- 产物纯净度：`jar tf target/toolnest.jar | grep -cE "^com/bytefuture/toolnest/.*(Probe|Test|Preview)"` = **0**

**起因**：用户要求重新设计 UI，先出设计图。

**现状诊断**（依据 `target/smoke/*.png` 真实渲染截图，非感觉）：

- 底色加一层：侧边栏 `#f6f7f9`→`#f2f4f7`，**内容区新增 `#f8f9fb`**，卡片保持 `#ffffff` → 靠底色差而非描边分层

- 图标族：Unicode → 统一线性 SVG（24 网格 / 1.9 描边 / 圆头），放 38px `#eef2ff` 方块
- 侧边栏选中态：主色实底 → **主色浅底 `#e8eefd` + 左侧 3px 主色条**；宽度 252 → 268
- 按钮三级：主操作实底（唯一）/ 次操作**描边**（替代现在的灰填充）/ 静默纯文字 / 破坏用危险色描边
- 页签两层：**外层胶囊滑块**（业务级）+ **内层下划线**（数据级）
- 结果行网格：标签定宽 96px、行高 34px、空值用 `—`（破折号）替代 `-`
- 表格给最小高度 3 行 + 「＋ 添加一行」空行引导

**三个必须记住的坑**
1. **`:drag-over` 不是 JavaFX 内置伪类**（只有 hover/focused/pressed/disabled/selected）。
   样式表里写 `.drop-zone:drag-over` 不报错、永不生效 —— 拖放高亮怎么调都不亮就是这个原因。
   必须 `PseudoClass.getPseudoClass("drag-over")` + `pseudoClassStateChanged` 从 Java 侧切换。
2. **同一容器同时挂两个样式类时，特异性相同 → 胜负只看文件顺序**。
   `.image-preview-holder` 定义在 `.drop-zone` 之后，于是虚线改不动。用组合选择器
   `.image-preview-holder.drop-zone` 提高特异性，从此不依赖章节顺序。
3. **探针必须与产品同源**：`SmokeTest` 原先没设 AtlantaFX 主题（跑内置 modena），
   截图里 CheckBox 文字被 ladder 算成浅色而「消失」，白排查了一轮。已补 `setUserAgentStylesheet(PrimerLight)`。
   给评审看的截图，探针环境必须先与产品一致。
