# 2026-09-24

## ToolNest 功能迭代：修缺陷 + 补齐空分类

先做了一轮代码通读（core / ui / 5 个模块 / 1145 行 CSS），识别出两个明确缺陷与
「9 个分类中 4 个为空」的机会点，随后按建议实施。

### 一、修复 JSON 缩进算法缺陷（真 bug）

`JsonFormatModule.pretty()` 原实现：先用 Gson 生成 2 空格缩进，再用 `reindent()`
按「行首空格数 ÷ 2」反推层级替换成目标缩进。

**问题**：该后处理无法区分「结构行」与「字符串值内容」，一旦字符串值里含换行
（如 `"line1\nline2"`），该行会被误判成结构行而套错缩进。

**修法**：改用 `JsonWriter.setIndent(indent)` 让 Gson 直接按目标缩进输出，
删掉整个 `reindent()`。注意 `setSerializeHtmlAsText` 在 `GsonBuilder` 上而非
`JsonWriter` 上，写出器这层对应的是 `setSerializeNulls(true)`；
`com.google.gson.internal.Streams.write(element, writer)` 可从外部调用。

### 二、ContentPane 返回栈 + 有界缓存

原来只能退回「上一次的宫格页」（只记 `currentCategory` / `showingAll` 两个状态）。

- 引入 `Deque<String> history` 存**页面 key**（不存 Node —— 页面被缓存淘汰后
  仍能凭 key 重建）。key 约定：`cat:XXX` / `mod:xxx` / `__all__`
- **两条必须遵守的规则**：① 返回操作本身不入栈，否则 A↔B 来回死循环；
  ② 目标 key 与当前相同则不记史，否则连点后退半步
- `detailCache` 换成 `LinkedHashMap(accessOrder=true)` + `removeEldestEntry`，
  上限 12 项。模块数会持续增长，无上限缓存 = 只增不减的内存泄漏
- **宫格页也加了返回按钮**（有历史时才显示）。这是实现过程中发现的**设计缺口**：
  原来宫格页完全没有返回入口，只能靠侧边栏横跳，多级历史根本用不上

### 三、新增 3 个模块（零新依赖）

| 模块 | 分类 | 说明 |
|---|---|---|
| `text/TextModule` + `TextOps` | TEXT | 去重/排序/去空行/大小写/加行号/正则替换/统计 |
| `file/FileHashModule` + `HashOps` | FILE | MD5/SHA-1/SHA-256/SHA-512，拖入多文件，流式+后台线程 |

### 四、踩到的坑（重要）

1. **`HBox` 没有 `setWrapText()`**，要自动折行必须换 `FlowPane`
2. **按下标取 HBox 子节点会取错**：`getChildren().get(2)` 拿到的是 `spacer`（Region）
   而不是下一个 Button，`(Button)` 强转直接 `ClassCastException`。
   **教训：混入非目标类型节点的容器，一律直接持有引用，不按下标取**。
   这个 bug 编译完全通过，只有真跑 `buildContent()` 才炸 —— 印证了「编译通过 ≠ 完成」
3. **`Application` 子类不能直接当 main class**，探针也必须包一层
   `XxxProbeLauncher` 普通类 + `Application.launch(XxxProbe.class, args)`
4. **控制台中文乱码**：GBK 终端解码 UTF-8 输出。判读方式是把输出重定向到文件，
   再用 Python 按 utf-8 解码读回，**不要**依赖控制台可见的中文做断言

## 续：图片模块 + 探针迁出主源码树 + HTTP 响应体高亮

### 六、图片处理模块（填补最后一个空分类）

- **关键决策**：JPEG 不支持透明通道，写出时**自动合成白底**（不是默认的黑色）。
  这是最容易出 bug 的点，`ImageTest` 专门断言「透明 PNG 转 JPEG 后为白色」
- 预览用 `SwingFXUtils.toFXImage()`，因此 `javafx-swing` 从「仅探针需要」
  升级为**运行时依赖**（pom 注释已同步更正）

验证：`ImageTest` **27/27 PASS**，`SmokeTest` 确认 IMAGE 分类宫格正常渲染、CSS 错误 0。

### 七、开发期代码迁出主源码树（`src/main` → `verify/src/main`）

**动机**：4 个探针 + 3 个 Launcher + `DesignPreview` 原本混在 `src/main/java`，
会被打进 fat jar —— 它们是开发脚手架不是产品功能，混进去让包体变大、
也让「什么是要发布的东西」变含糊。

**做法**：新建与 `src/` 平级的 `verify/src/main/java/`，新增根目录 `verify.cmd`。

`verify.cmd` 原理：探针只用应用的公开 API，所以先 `mvn package` 打出 fat jar，
再把 `verify/` 源码编译进 `target/verify-classes`，以「fat jar + 探针 class 目录」
为 classpath 运行。**不需要任何额外 Maven 插件**（先试过
`build-helper-maven-plugin` 的 `add-source`，但本机离线仓库缺它的传递依赖 `bsh`，
干脆放弃）。

结果：fat jar 中探针类数量 **0**。

### 八、HTTP 响应体 JSON 语法高亮

`SingleRequestPanel` 的 Body 页签原来是一个纯 `TextArea`（全文单色）。

- 改为 `StackPane` 里**叠放两个视图**：`JsonCodeArea`（RichTextFX，按区间着色）
  与 纯文本 `TextArea`，按内容在两者间切换 `visible`/`managed`
- 判定规则：`trim` 后以 `{...}` 或 `[...]` **成对包裹**才算「值得高亮的 JSON」；
  裸字符串/数字走纯文本（高亮它们反而怪）
- **超过 256KB 不做高亮**：逐字符跑正则 + 构建 StyleSpans 常数很大，几 MB 响应会
  卡死 UI 线程；这类响应本来就该靠搜索定位
- 新增「**格式化 / 压缩**」按钮往返切换；非 JSON 时置灰
- 为可测试性加了 6 个**包级可见**的测试钩子（`applyResultForTest` 等），
  探针因此放在 `modules.http` 包内

验证：新增探针 `HttpBodyProbe` **22/22 PASS**，含 JSON 分流、格式化往返幂等、
非法 JSON 降级、超大响应降级、清空后状态复位。截图人工核对配色正确。

### 九、本轮踩的坑（cmd 脚本三连）

写 `verify.cmd` 时连续踩了三个坑，每个都表现为莫名其妙的编译错误：

1. **JDK 21 的 `javac` 不接受单横杠长选项 `-release`**，必须写 `--release 21`。
   报「无效的标记: -release」。直接用 Git Bash 调 javac 也一样，
   **与 cmd 无关**，是 javac 本身的行为
2. **`@argfile` 里的路径必须用正斜杠**：argfile 中反斜杠是转义符，
   `D:\Person\...` 被吃成 `D:Person...`（`\t` 还变成制表符）
3. **`for /r` 拿到的路径是反斜杠**，要在 cmd 里转换需
   `setlocal enabledelayedexpansion` + `set "p=!p:\=/!"`；
   注意 `endlocal` 会丢掉块内设的变量，`ARGFILE` 要设在 `setlocal` 之前

另外：`verify.cmd` **默认每次重建 fat jar** —— 探针编译链接到 jar 上，
用旧 jar 会报 "cannot find symbol"，非常难排查。只想改探针代码时传 `-nobuild` 跳过。

## 续二：二维码生成与解析模块

`modules/qrcode/QrModule.java` + `QrOps.java`，归入 GENERATE 分类。
解析的三种输入都走同一条管线：**选择文件 / 剪贴板 Ctrl+V / 拖入**。

### 十一、依赖决策：只引 ZXing `core`

```xml
<dependency>
  <groupId>com.google.zxing</groupId>
  <artifactId>core</artifactId>
  <version>3.5.3</version>
</dependency>
```

**刻意不引 `javase`** —— 它会连带拉进 `jcommander` + `jai-imageio-core` 两个
本工具完全用不到的依赖（体积 + 依赖面）。`javase` 只提供
`BufferedImageLuminanceSource`、`MatrixToImageConfig` 这类胶水类，
自己写约 40 行 `LuminanceSource` 子类即可替代。`core` 运行时零传递依赖。

**踩坑**：最初 `import com.google.zxing.client.j2se.MatrixToImageConfig` →
编译期就找不到（那类在 `javase` 里）。改为自己写
`toBufferedImage(matrix, onColor, offColor)`，直接传 int ARGB。

### 十二、解析链路的关键设计

1. **降级策略三级重试**：原图 → 放大 3 倍 → 高对比度灰度。
   小码 / 浅色码 / 带干扰截图靠这一步救回来
2. **多码支持**：`QRCodeMultiReader.decodeMultiple()` 先试；
   **注意 `MultiFormatReader` 没有 `decodeMultiple()`**（只有 `MultipleBarcodeReader`
   有），所以回退时调 `MultiFormatReader.decode()` 走单码
3. **失败归因**：`Failure` 枚举区分 NOT_FOUND / FORMAT / CHECKSUM / UNKNOWN，
   各带中文 `message()`，不笼统报「识别失败」
4. **框选裁切**：坐标换算 `scaleX = source.width / shown.width`，
   并向外留 **1/8 边距** —— 用户框得比码略小时会切掉定位角，留边距能救回来
5. **剪贴板优先级**：图片 → 文件 → 文本，逐级探测并给对应提示。
   避免「复制了文本却提示无法识别图片」的误导

### 十三、生成侧的设计

- 参数：纠错级别（L/M/Q/H，附容量提示与适用场景）、尺寸、留白、前景/背景色
- 预览 `setSmooth(false)` —— 保证码点边缘锐利，所见即所得才是真正要被扫的那张
- `Level` 枚举带 `tag()/ratio()/note()/toZxing()`，把「约 15%」这类说明和
  ZXing 常量绑在一处

### 十四、测试发现的两个真 bug

1. **过期图残留（真 bug）**：`generate("")` 原本提前 return，
   没有清空 `generated` 字段，用户清空输入后**仍能「导出」上一次的码**。
   修法：抽出 `discardGenerated()`，空输入与异常路径都调用。
   这个 bug 是探针断言「清空输入后不再持有可导出的图」逼出来的
2. **密度断言不成立（测试自身的问题）**：原本断言「H 级比 L 级码点更密」，
   在 400px 下测出 L=0.293 / M=0.271 / Q=0.276 / H=0.284 —— **非单调**。
   根因：400px 下像素栅格取整噪声淹没了密度信号。实测在 **1200px** 下
   单调成立（L=0.293 / M=0.308 / Q=0.314 / H=0.328），改测试为 1200px 测量

### 十五、探针截图全黑的排查（重要经验）

生成页截图最初是**一整块黑方块**，但实际 PNG 数据完全正确
（43520 黑 / 116480 白），FX 侧 `toFXImage()` 也验证过
（`FX(200,200)=0x000000ff`，白色像素 113632 个）。

**根因**：`applyCss() + layout()` 只保证**布局**完成，**不保证绘制**。
刚 `setImage()` 就立刻 `snapshot()`，捕获到的是未绘制的空区域。

**修法**（探针专用）：`Platform.runLater` 嵌套 3 层再截图，
给绘制脉冲留出时间。**这是探针测试手法的问题，不是产品缺陷** ——
应用里用户看到的是正常的。

> 又踩了一次 **漏写 `package` 声明** 的坑：临时 `DensityProbe.java` / `QrDump.java`
> 编译"成功"但类落在 default package（`target/verify-classes/XxxProbe.class`），
> 运行时找不到。用完即删。

## 续三：修复二维码模块两个用户上报的真 bug

用户报了两个现象：① 生成二维码「全黑」；② 解析页「无法粘贴裁切版」。
两个都是**真 bug**，而且都逃过了此前 179 条探针 —— 值得记下来。

### 十七、Bug 1：生成图全黑 —— 颜色分量漏乘 255

**根因**（`QrModule.toAwt()`）：

```java
// 错误：JavaFX Color.getRed() 返回的是 0.0–1.0，不是 0–255
new java.awt.Color((int) Math.round(c.getRed()),
                   (int) Math.round(c.getGreen()),
                   (int) Math.round(c.getBlue()));
```

白色 `(1.0,1.0,1.0)` → `Math.round(1.0)` = **1** → `#010101`。
黑色 `(0.0,0.0,0.0)` → `0` → `#000000`（**恰好仍然正确**）。

> 极隐蔽的地方就在这：**黑色是对的**，所以肉眼看到的是「黑底 + 几乎看不见的
> 暗纹」，很自然会怀疑是渲染问题 / CSS 问题 / ImageView 问题，
> 而不会想到是颜色换算。实际图像数据里白像素全变成了 `#010101`。

**修法**：`Math.round(c.getRed() * 255)`，三个分量都补上 `* 255`。

**这段排查过程本身值得记**：我写了好几轮「隔离复现」，全都**通过**了 ——
因为我在探针里直接调 `QrOps.generate(text, opts)` 并手写 `Color.BLACK/WHITE`，
**绕过了 `toAwt()` 这一层**。真正定位到的关键一步是：
在**真实模块**里生成后，去读 ImageView 里那张图的像素（而不是自己造的图），
看到 `(0,0)=0xFF010101`、`black` 数与干净对照**完全相同**、`white=0` —
黑对白错 → 立刻指向「只有白色这一路被改写」→ 颜色换算。

**教训**：隔离复现一旦全部通过，说明探针**没有复现真实调用链**。
这时要停止造简化场景，改为**在真实对象上取数据**。

### 十八、Bug 2：Ctrl+V 无法粘贴

**根因**：过滤器挂在 `decodeStage`（预览区 StackPane）上：

```java
decodeStage.addEventFilter(KeyEvent.KEY_PRESSED, e -> { ... });
```

但键盘焦点实际停在 **TabPane** 上（实测 `scene.getFocusOwner()` = `TabPane`），
点一下预览区也抢不到焦点 —— 按键事件根本到不了那个节点。

**修法**：改挂在 **Scene** 上，用 `root.sceneProperty()` 监听在节点入场景时装上、
离场景时摘掉。另加两道闸：① 事件目标是 `TextInputControl` 时不响应（让位给原生
文字粘贴）；② 根节点已离开场景（模块被切走）时不响应。

**修法验证的关键**：探针必须**从 Scene 派发事件**（`Event.fireEvent(scene, ev)`），
直接调 `pasteFromClipboard()` 是测不出「过滤器装错节点」这个 bug 的。
`firePasteShortcutForTest()` 因此刻意走真实过滤器链路。

### 十九、本轮踩的探针自身的坑（三个）

1. **读错了 ImageView**：`QrModule` 生成页与解析页各有一个 ImageView，
   解析页那个嵌在 `selectionLayer` 里。用 `findByClass(ImageView).get(0)`
   拿到的是生成页的（`image=null`），于是误判「粘贴失败」。
   **判据要选对**：改按「`image-preview-holder` 里第一个 ImageView」定位。
2. **读错了 TextArea**：结果框与生成页输入框都是 TextArea，
   `get(0)` 可能拿到输入框。改按样式类 `qr-result` 精确定位。
3. **断言顺序耦合**：第 5 步 `generateForTest("")` 会作废 `generated`，
   第 6 步再取 `generatedForTest()` 就是 null → NPE。
   跨步骤共享状态时，后一步必须自己重新建立前置条件。

## 续四：Bug 3 —— 粘贴透明背景图「发白 + 识别不出」

用户反馈：裁切版**能粘贴了**（Bug 2 已修好），但「颜色不对，识别不出来」。
截图里二维码清晰可见，只是整体发白发灰。

### 二十二、根因：透明像素的 RGB 是 0（黑），ZXing 只看亮度

**现象 → 原理**：截图工具（微信/QQ 截图的圆角、无底色区域）产出的图**带 alpha**。

- **识别失败**：ZXing 走 `LuminanceSource` 取亮度。透明像素 `0x00000000` 的
  RGB 是 `0` → 被判成**纯黑**。一张「白底黑码」的图变成「全黑」→ 必然识别失败。
- **界面发白**：透明区域不做处理时露出容器的浅灰底纹，视觉上就是「发白」。

**实测数据**（造透明背景二维码，280px）：

```
输入图（透明背景）type=3 平均alpha=75
  直接解析 = ❌ 失败                    ← 复现用户现象
走真实模块链路（修复后）:
  decodeImageForTest = ✅ TRANSPARENT-TEST-2026
  预览源图 type=1 平均alpha=255        ← 已消除透明
  预览源图纯白像素=63270
```

**修法**：`setDecodeImage()` 入口统一 flatten 到白底。

```java
private static BufferedImage normalizeForDecode(BufferedImage img) {
    if (img == null || !img.getColorModel().hasAlpha()) {
        return img;                     // 无 alpha 不做多余复制
    }
    return ImageOps.flatten(img, java.awt.Color.WHITE);
}
```

**复用而非重写**：`ImageOps.flatten()` 早已存在（图片模块转 JPEG 时也要
「透明合成白底」，MEMORY 里记过「JPEG 无透明通道必须合成白底」这条）。
同一个坑在两个模块各踩一次 —— 这次直接复用现成实现。

**关键点**：三条入图路径（选择文件 / 拖入 / 剪贴板粘贴）**都汇流到
`setDecodeImage()`**，所以只需在这一处修，覆盖面是完整的。

## 续五：Bug 4 —— 「粘贴裁切版识别不出」

用户再次上报：粘贴裁切版，识别功能不能用。

### 二十六、【修正后】根因：AWT ↔ JavaFX 剪贴板互操作缺陷

> ⚠️ **重要：本节最初写成「预乘 alpha 摧毁透明像素 RGB」，那个归因是错的，
> 已被受控实验推翻。以下是修正后的正确结论。保留错误过程作为方法学教训（见三十）。**

**真实根因：图片以「原生/AWT 方式」放到剪贴板（截图工具就是这么放的）时，
JavaFX 的 `Clipboard.getImage()` 返回一张损坏的、全透明的图 —— 每个像素 alpha 被清零，
且尺寸掉 1 像素。**

剪贴板矩阵实验（谁写 × 图是否带 alpha），规律极干净：

| 组 | FX `getImage()` 读回 | 结果 |
|---|---|---|
| **AWT 写** / RGB 不透明 | 299×299，**全透明** | ❌ |
| **AWT 写** / ARGB 有透明 | 299×299，**全透明** | ❌ |
| FX 写 / ARGB 有透明 | 300×300，像素完好 | ✅ |
| FX 写 / ARGB 全不透明 | 300×300，像素完好 | ✅ |
| AWT 写 / **AWT 读**（对照） | 300×300，像素完好 | ✅ |

决定性像素统计（AWT 写、FX 读，300×300 透明 QR）：
```
源图   300x300 黑=18630 透明=71370   →  识别 OK
FX 读  299x299 黑=0     透明=89401   →  识别 null   ← 整张全透明
```
**注意 `黑=0`：连 alpha=255 的不透明黑码点都变透明了** ——
这不是预乘（预乘对 `0xFF000000` 是恒等变换），是**互操作层把 alpha 通道整体丢了**。

模块自身的 `flatten` **逻辑正确**：它忠实把这张「全透明纸」合成成纯白，
于是用户看到「预览区空白 + 未识别到二维码」，与截图现象逐字吻合。

### 二十七、修法：`pasteFromClipboard()` 改「AWT 优先，JavaFX 兜底」

```java
// 首选 AWT：绕开 FX 的互操作层，尺寸与像素都完好
java.awt.datatransfer.Clipboard cb =
        java.awt.Toolkit.getDefaultToolkit().getSystemClipboard();
if (cb.isDataFlavorAvailable(DataFlavor.imageFlavor)) {
    Object d = cb.getData(DataFlavor.imageFlavor);   // 非预乘 BufferedImage
}
// 拿不到 / 抛异常（cannot open system clipboard）→ 优雅退回 FX 路径
```

决定性验证（AWT 写剪贴板的前提下）：

```
[透明背景图] [A] FX 读 299x299 → 识别 null（黑=0 白=89401 全白）
             [B] AWT 读 300x300 → 识别 OK（黑=17010 白=72990）  ✅
[不透明RGB]  [A] FX 读 299x299 → 识别 null（黑=0 白=89401 全白）
             [B] AWT 读 300x300 → 识别 OK（黑=18468 白=71532）  ✅
```

**AWT 读一次性解决两个问题**：绕开互操作损坏 **+** 不再掉 1 像素。

`Dragboard.getImage()`（拖入路径）走的是 FX 自己的通道，矩阵实验显示**正常**，
无需修改。

### 二十八、探针设计教训（第三次踩「绕过真实链路」）

续四的探针漏掉这个 bug，是因为它**自己造内存里的透明图、绕过了剪贴板往返**。
正确做法：探针必须**真的把图放进系统剪贴板**（且要用 AWT 方式写，
因为那才是截图工具的方式）再读回来。

> **凡是「外部系统边界」（剪贴板 / 文件 / 网络），都不能用内存对象顶替。**
> 而且还要进一步区分**边界两侧的实现是谁**（AWT vs FX）——
> 本次的 bug 恰恰就藏在这个「两侧实现不一致」的缝隙里。

### 二十九、验收断言（两条 + 一条反向）

1. 「AWT 方式放入剪贴板 → 修复后的 `pasteFromClipboard()` 能识别出内容」
   —— 修复前必须失败、修复后必须通过
2. 「粘贴后 `decodeSource` 尺寸与原图一致」（不掉 1 像素）
3. **反向断言**：「FX 读同一张剪贴板图会得到全透明结果」
   —— 把「为什么必须走 AWT」固化住，防止将来有人改回 FX 路径

素材至少要覆盖 **透明背景 QR** 与 **不透明 RGB QR** 两种（两种都会坏）。

### 三十一、AWT 与 FX 剪贴板**不可混用**（9c 被放弃）

落地回归断言时，我原计划加一条反向断言：先在 AWT 写入剪贴板，再用
FX 的 `Clipboard.getSystemClipboard().getImage()` 读回来，断言它全透明。

**结果：JVM 直接崩溃退出** —— 9b 之后既无 9c 输出，也无 CSS 断言，
更无 `RESULT` 汇总行，进程静默消失。

这与早先 `PasteDecodeProbe` 的崩溃是**同一模式**。结论：

> **在 AWT 刚写过系统剪贴板之后，立刻用 JavaFX 读同一份剪贴板内容，
> 会让 JVM 崩溃（非异常，是进程级死亡）。两条剪贴板链路混用不安全。**

对策：
- 回归断言**只用正向路径**（AWT 写 → 产品代码 AWT 读 → 断言识别成功），
  足够区分修复前后行为，不做「FX 读」的反向断言。
- 产品代码里 `pasteFromClipboard()` 的降级顺序（AWT 优先 → AWT 返回 null
  才退回 FX）是**安全**的：退回 FX 的前提是「剪贴板里没有图」，
  此时 FX 读也不会崩。
- **切勿**在同一个探针里既用 AWT 读写剪贴板又用 FX 读剪贴板。

### 三十二、界面探针新增钩子：`putImageOnAwtClipboardForTest`

### 三十六、探针卡死的真实原因（环境残留，非代码缺陷）

排查过程中探针多次「跑满 4–5 分钟不退出」。用 `jstack` 抓栈定位：

- `JavaFX Application Thread`：RUNNABLE，正常跑在 `WinApplication._runLoop`
- `InvokeLaterDispatcher`：**DAEMON + WAITING** ← 派发器已停摆
- `AWT-Windows`：DAEMON（**是守护线程，不阻止退出**）

**结论**：卡死源于**上一轮被 kill 的探针进程留下了未释放的 AWT 剪贴板占用**，
新一轮的剪贴板调用发生调度竞争。清掉孤儿进程后，
**连续 3 次运行均稳定 35/35、约 3 秒干净退出**。

> **教训**：
> 1. 用 `&` 起后台 java 进程时，`kill $!` 只杀到 bash 包装，
>    **杀不到 JVM**。收尾必须用 `jps -l | grep <主类>` 找真实 PID 再杀。
> 2. **Git Bash 下 `taskkill //PID`（双斜杠）会报「无效参数」**。
> 3. 探针「卡住」时，先查有无**孤儿 JVM 残留**，再怀疑代码。

### 三十七、界面探针收尾必须 `System.exit`

`QrModuleProbe.finish()` 原本只调 `Platform.exit()`。
本次引入 AWT 剪贴板后，`Platform.exit()` 不足以让进程退出
（AWT 相关线程 + FX 线程生命周期交织），实测挂住不返回。
改为 `System.out.flush(); System.exit(failed > 0 ? 1 : 0);` 后立即干净退出。

> 附带好处：`System.exit` 的退出码让 `verify.cmd` 能正确反映失败
> （`if errorlevel 1` 分支），断言失败不再被静默吞掉。
> 同时**给探针加了一个 `clearDecodeResultForTest()` 钩子**：
> 异步断言（7b）重放前必须先清空结果框，否则上一轮遗留文本
> 会让「结果非空」这个完成判据立刻为真，断言退化成读旧值。

## 续六：Bug 5 —— 框选起点不跟随鼠标落点

### 三十八、根因：两处尺寸/坐标换算都用了「原图尺寸」当「显示尺寸」

用户上报：框选时，蓝色矩形**起点不跟随鼠标落点**（截图中鼠标在码左下，
框却偏在右上）。排查发现**两个独立缺陷叠加**：

**缺陷 A：`selectionLayer`（框选层）尺寸与图片实际显示尺寸失配**

```java
// 旧代码 —— 各自独立截断到上限
selectionLayer.setPrefWidth(Math.min(fx.getWidth(), PREVIEW_MAX));   // 460
selectionLayer.setPrefHeight(Math.min(fx.getHeight(), PREVIEW_MAX)); // 460
```

但 `decodePreview` 是 `preserveRatio=true` 的**等比缩放**。
对 1200×800 的图：等比显示是 **460×306**，旧算法给出 **460×460** ——
框选层比图片高 154px，图片在其中居中 → 坐标系整体下移 77px。

**缺陷 B：`cropFromSelection()` 的缩放比恒等于 1**

```java
double shownW = fx.getWidth();   // ← JavaFX Image.getWidth() 返回**原图宽**！
double scaleX = decodeSource.getWidth() / shownW;  // = 原宽/原宽 = 1  ← 恒等
```

`fx` 是 `decodePreview.getImage()`，**`Image.getWidth()` 是原图尺寸**，
所以 `scaleX/scaleY` 恒为 1，裁切**完全没做缩放换算** ——
用显示坐标系（≤460）的框去裁原图坐标系（可能 1200+）的区域，必然错位。

> **这两个缺陷叠加才构成用户看到的现象**：画的框位置是偏的（A），
> 即使框对了裁出来也是错的（B）。

### 三十九、修法：抽出 `displaySize()` 作为唯一真相源

新增私有静态方法，按 `ImageView(preserveRatio + fitW/H)` 的规则算等比显示尺寸：

```java
private static double[] displaySize(double srcW, double srcH) {
    double scale = Math.min(1.0, Math.min(PREVIEW_MAX / srcW, PREVIEW_MAX / srcH));
    return new double[]{srcW * scale, srcH * scale};
}
```

三处共用它：① 设 `selectionLayer` 尺寸 ② `cropFromSelection()` 的缩放比
③ 探针核算。**同一份语义只维护一处** —— 这正是 MEMORY 里已记的
「同一份内容的解析与显示必须走同一条路径」在坐标换算上的翻版。

**额外一步（由端到端探针发现）**：把小图的 `decodePreview.setFitWidth/Height`
也收紧到 `shown`。因为 `fitWidth=460` 时 ImageView 的 **pref 尺寸仍是 460**
（fit 只是上限，不缩小 pref），而 `selectionLayer` 的 pref 是小图尺寸（如 350），
二者同处 StackPane → StackPane 取子节点**最大 pref** → 框选层被撑回 460。
把 fit 设成 shown 后，ImageView 真实占用 == shown，不再有谁撑谁。

### 四十、新增端到端探针 `SelectionE2EProbe`（已纳入 `verify.cmd sel`）

`QrModuleProbe` 的 3b/3c 段只用一个尺寸的图，**漏掉了宽高比变化**。

| 用例 | 等比显示 | 旧算法 | 结果 |
|---|---|---|---|
| 1200×800 横向 | 460×306 | 460×460 ❌ | 「识别失败」 |
| 900×1400 纵向 | 295×460 | 460×460 ❌ | 「识别失败」 |
| 900×900 正方形 | 459×459 | 460×460 ⚠️ | 「识别失败」 |
| 350×350 小于上限 | 350×350 | 460×460 ❌ | 「识别失败」 |

与用户现象逐字对应。恢复修复后 **12/12 全绿**。

> **正方形用例的尺寸断言恰好通过（460 对 460）**，
> 但裁切断言仍失败 —— 这正说明**缺陷 A 与 B 是两个独立的 bug**，
> 只修一个都不够。设计用例时必须覆盖「宽高比 ≠ 1」才算数。

### 四十一、探针手法：`getWidth()` 需要布局后才反映 `setPrefWidth`

`SelectionE2EProbe` 第一版全部报「框选层=460×460」，一度以为是修复无效。
实际是：**`setPrefWidth()` 只设期望值，`getWidth()` 要等布局完才更新**。
`decodeImageForTest()` 之后必须补 `root.applyCss(); root.layout();`。

> 这是**探针手法问题，不是产品缺陷**（真实应用里布局由 JavaFX 自动完成）。
> 与 MEMORY 里已记的「`applyCss()+layout()` 只保证布局不保证绘制」同源 ——
> 但那条讲的是**绘制**，这条讲的是**布局生效**，两者都要注意。

### 四十二、`MouseEvent` 在离屏探针里用 `fireEvent` 到不了 handler

想模拟真实鼠标拖拽时，`Event.fireEvent(selectionLayer, mouseEvent)` **完全无效**
（handler 未被调用，读到的还是上一轮残留值）。原因：JavaFX 鼠标事件派发
依赖完整 Scene/Window 与 pick 结果，离屏环境不具备。

**改用直接调用 handler 本体**：

```java
selectionLayer.getOnMousePressed().handle(mouseEvent(MOUSE_PRESSED, x, y));
```

handler 内部仍是 `imageLocalPoint()` 换算 + 真实的 `dragStart/selectionRect` 逻辑，
**待验证的换算代码一行都没绕过**，覆盖度与真实派发等价。
（这与 MEMORY 里「无头截图验证：直接驱动真实控件 + `button.fire()`」同一思路。）
