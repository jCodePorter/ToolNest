# 批处理「① 请求模板」段 —— 对齐单一请求页样式（spec v1）

> 状态：**已批准并实施（2026-10-03）**。实施后的 JavaFX 实测口径见 §7。
> 范围：仅 `BatchPanel` 段①。不动段② CSV、段③ 执行配置与结果，不动批处理页的三段折叠模型。

---

## 1. 诊断

### 1.1 症状与根因

截图里段① 读起来像「另一个应用」：字段标签（`请求地址模板` / `请求体类型`）、
下拉框、收起式 `TitledPane`，而单一请求页是「方法+URL 一条横带 + 页签 + 工具行」。

根因一句话：**段① 还在用「表单面板」的控件词汇（field 标签 + ComboBox + TitledPane），
而单一请求页已经换成「请求编辑器」的词汇（请求行 + 页签 + 分段控件 + 工具行）**，
两页没共用同一套编辑器组件。

### 1.2 逐项差异

| # | 维度 | 批处理段①（现状） | 单一请求页（目标） |
|---|---|---|---|
| 1 | 地址 | `field("请求地址模板", …)` 左标签 + 方法 + URL | 无标签，方法与 URL 同一条横带 |
| 2 | 请求体类型 | `ComboBox` 下拉（宽 180） | `ToggleGroup` 分段控件（7 项） |
| 3 | 请求头 | 收起的 `TitledPane`，藏在最下面 | 独立页签，与 Params / Body 平级 |
| 4 | 占位符说明 | 另起一行（不存在，段① 没写） | 内联在请求行右端 |
| 5 | 表单标签 | 每行一个左标签，行高 32 | 无标签，靠工具行右端挂说明 |
| 6 | 降级说明 | 跟在「请求体类型」下拉右侧 | 跟在分段控件右侧（同一做法） |

### 1.3 现状竖向账（段① ≈ 190px）

| 区域 | px | 备注 |
|---|---|---|
| 请求地址模板（标签 32 档） | 32 | |
| 请求体类型（标签 32 档） | 32 | |
| 请求体模板 TextArea | 48 | 约 3 行 |
| 请求头 TitledPane（收起） | 38 | |
| 正文间距 8×3 | 24 | |

| **合计** | **190** | |

## 2. 方案：段① 换成「请求行 + 页签」

### 2.1 结构

```
┌ ① 请求模板 ─────────────────────────────────────────┐
│ [GET ▾] https://api.example.com/order?orderId={orderId}   36  请求行
│                                    支持 {列名} 占位符 ↑   (内联右端)
│ ┌ Params │ Headers(2) │ Body·JSON ┐                        42  页签轨道
│ │ [分段控件 无|JSON|Form|XML|Text] [Content-Type…] [格式化] │  38  工具行
│ │ { "orderId": "{orderId}" }                                    │  48  编辑器
│ │ }                                                            │
│ └────────────────────────────────────────────────────────────┘
└──────────────────────────────────────────────────────────────┘
```

### 2.2 与单一请求页的对齐点

- **请求行**：方法下拉 + URL 输入框 + 右侧内联说明。去掉 `field()` 左标签。
  右侧留空档给「占位符说明」——这正是单一请求页 `statusBox` 的位置。
- **页签**：`Params` / `Headers` / `Body` 三页签，与单一请求页同名同序。
  批处理页**新增 `Params`**（query 参数，CSV 场景下常用），`Body` 页签标题带项数。
- **工具行**：`Body` 页签内用分段控件代替下拉，右侧挂 `Content-Type` 与动作槽
  （`JSON` 类型给「格式化」）。降级说明仍挂在分段控件右侧。
- **Headers 页签**：复用刚做完的键值表 + `+ JSON` / `+ Token` / `+ 新增请求头` / `清空` 工具行。

### 2.3 竖向预算（段① 卡片 = 244px，浏览器实测）

| 区域 | px | 备注 |
|---|---|---|
| 请求行（方法 36 + URL 36，同一行） | 36 | `.http-method` / `.http-url` 都是 36 强调档 |
| 页签轨道 | 42 | 轨 38 + 下留白 4 |
| 工具行（分段控件 + Content-Type + 动作槽） | 38 | `.http-type-seg` 抬到 32，与工具行等高 |
| 请求体编辑器（JSON 文本区） | 48 | 3 行，沿用现状口径 |
| 正文间距 8×3 | 24 | 4 个子节点 |
| 正文上下内边距 8×2 | 16 | `.stage-body-compact` 沿用 |
| **正文合计** | **204** | 36+42+38+48+24+16 |
| 卡片头 38 + 上下边框 1×2 | 40 | |
| **段① 卡片实测高** | **244** | `getBoundingClientRect` 实测 244 |

### 2.4 整页一屏校验（关键）

| 区域 | px | 备注 |
|---|---|---|
| 段① 请求模板 | 244 | 本文方案（实测） |
| 间距 | 10 | |
| 段② CSV 数据（收起） | 38 | |
| 间距 | 10 | |
| 段③ 执行配置与结果 | 340 | `RESULT_MIN_H` 预留，不变 |
| **合计** | **642** | ≤ 653，一屏内，余 11px |

> **两处取舍都是在浏览器实测后才发现的，不是推算出来的：**
>
> **① 占位符说明必须内联到请求行右端。** 单起一行是 264px，整页超预算。
> 单一请求页本来就是这么做的（`statusBox` 与请求行同行），所以这不是权宜之计。
>
> **② 请求体编辑器只能给 3 行（48px）。** 最初画的是 4 行（76px），
> 段① 卡片实测 272px → 整页 670px，**超预算 17px**，段③ 底部会被切掉一小截。
> 回到 3 行后 244px / 642px，余 11px。
>
> 这正是「结构断言全绿 ≠ 长得对」：四个子节点都在、样式也都对，
> 但竖向账只有在浏览器里量 `getBoundingClientRect` 才暴露。
> **第一版预算表把「正文 232」当成了「卡片 232」，漏了头 38 和边框 2** ——
> 尺子刻错比画布画错更危险，所以校验器把「标尺标签 == 实测高度」当成硬断言。

## 4. 需你拍板的三个取舍

**Q1 · 批处理页要不要新增 `Params` 页签？**
单一请求页有 `Params`（query 参数）。批处理页现在没有，CSV 场景下「地址里带
`{列名}` 但想单独列 query 参数」的需求是常见的。
- A（推荐）：加，与单一请求页三页签完全对齐
- B：不加，只做 `Headers` / `Body` 两页签，少一层嵌套

**Q2 · 段① 要不要取消折叠？**
段① 现在可折叠，收起时头带显示 `GET  https://…` 摘要。
- A（推荐）：保留。CSV 导入与开始执行时都会自动收起它，是既定流程
- B：取消常驻展开，省掉头带 38px（段① 变 206px），但失去摘要

**Q3 · 「请求体类型」下拉换成 7 项分段控件会不会太挤？**
批处理页实际只支持 5 种（`batchTypes()` 不含 `FORM_DATA` / `BINARY`，
因为它们只有「路径」没有「值」，`{列名}` 占位符无意义）。
- A（推荐）：只列 5 项（无 / JSON / Form / XML / Text），不给点了会出错的入口
- B：列全 7 项与单一请求页一致，点了就提示「该类型不支持占位符」

## 7. 实施后的实测（JavaFX 口径，与设计稿的浏览器口径不同）

设计稿是浏览器口径，实施后 JavaFX 的三个数都不一样，**实施时以实测为准**：

| 区域 | 设计稿（浏览器） | 实测（JavaFX） | 差在哪 |
|---|---|---|---|
| Body 页签内容 | 42 + 48 = 90 | 96 | 编辑器实测 50（不是 48） |
| 内层页签整体 | （不拆） | 154 | 轨 **43.33** + content-area padding **14** + 内容 96 |
| 段① 卡片 | 244 | **252.7** | 轨比设计稿的 42 高 1.33，且 padding-top 14 设计稿没算 |

**三个数都是实测的，不是估的** —— 少任何一个，编辑器就被 TabPane 裁掉。

### 实施中撞到的三个真问题

1. **不能复用 `.http-req-tabs`**（钉死 312，那是单一请求页给 210px 编辑器留的）。
   套过来段① 从 244 涨到 **456**、整页 855，段③ 被整段推出视口。
   → 新增 `.batch-tabs` 专用类。
2. **工具行必须在页签内部**。放到 TabPane 外面会变成「页签+编辑器」一块、
   「工具行」一块 —— 工具行跑到编辑器下面去了，而且切页签时它不该跟着换页。
3. **`bodyBox` 不能写死高度**。写死 94 与内容（38+8+50=96）差 2px，
   那 2px 正好把编辑器顶出可视区。

### 最重要的一条教训

> **探针量高度量不到「被父容器裁掉」。**

TabPane 装不下时会把内容裁掉，而 `bodyArea.getHeight()` 仍然是 50px ——
节点在、尺寸对、visible=true。**32 条断言全绿，截图上编辑器只剩一条边。**

所以补了一条判据不同的断言：`bodyEditorFullyVisibleForTest()` 断的是
「编辑器底边 vs **TabPane 的 content-area** 底边」。注意**不能跟 `bodyTabContent` 比** ——
它自己也会被压扁，跟它比永远「没超出」，那条断言在 TabPane 只有 110 时实测仍为 true，
**等于恒真**。恒真断言比没有断言更危险。

反向验证：TabPane 154 → 110 时该断言转红（`编辑器完整可见 = false`）。

### 顺带的效果

段① 变矮后省下的高度归段③：结果表从 230.67（5 行）涨到 **278.67（8 行）**，
那条跑了很久的既存红「配置态结果表 ≥ 6 行」**自动转绿**。

  整页铺满、段③ 拿到余量、降级说明在位、JSON 态解除降级、页签切换不丢内容、
