## 1. 目标与验收口径

### 1.1 用户诉求的翻译

用户原话：**「切换请求类型时，对应的输入框也没有跟着调整，如切换 form 时，应该是 key/value 形式，且支持选择本地文件。」**

拆开是三件事，缺一不可：

| # | 诉求 | 现状 | 本轮处置 |
|---|---|---|---|
| R1 | **类型切换要换编辑器形态** | 5 种类型共用一个 `TextArea`，切类型只改不透明度 | 每种类型一个专属编辑器，切换时真的换节点 |
| R2 | **Form 是 key/value 形式** | 是纯文本框，用户得自己拼 `a=1&b=2` | 换成键值表，与 Params / Headers 同一套组件语言 |
| R3 | **支持选择本地文件** | `BodyType` 枚举里**没有 multipart**，完全无法上传 | 新增 `Form-data`（逐行文本/文件）+ `Binary`（单文件） |

「粗糙」的其余表现（详见设计稿 §01 的 D1–D13）都归到这两条根因：
**① 一个控件承担多种语义；② 纵向 chrome 吃掉 134px，把响应区挤出首屏。**

### 1.2 可断言验收项（交给后续验证）

| # | 指标 | 定义 | 改造前 | 本轮目标 |
|---|---|---|---|---|
| M1 | **请求体编辑器与类型一致** | 逐类型断言编辑器节点类型 | 恒为 `TextArea`（5 种类型全一样） | `NONE`→空态 / `JSON`·`XML`·`Text`→`TextArea` / `FORM`→键值表 / `FORM_DATA`→form-data 表 / `BINARY`→单文件选择器 |
| M2 | **键值表可见行数** | `(表高 − 表头 40) ÷ 34` | **3.3 行**（表 152） | **5.0 行**（表 210） |
| M3 | **请求体文本区可见行数** | `文本区高 ÷ 18` | **≈ 6 行**（127px） | **11 行**（210px） |
| M4 | **响应区可见行数（查看态）** | `(内容高) ÷ 18` | **≈ 10 行**（187px） | **24 行**（432px） |
| M5 | **chrome 高度** | 详情页头 85 之后、第一块内容之前 | **134px** | **64px**（省 70） |
| M6 | **首屏是否出现外层滚动条** | 内容自然高 vs 视口 678 | 溢出 23px（内容 701） | **不溢出**（配置态 763 铺满；查看态铺满） |
| M7 | **Form 编码真实生效** | 服务端收到的字节 | 原文未编码（`城市=北京 上海&n=1` 原样发出） | 按 RFC 3986 百分号编码 |
| M8 | **multipart 真的能发出** | 服务端解析到的段 | 无此能力 | boundary + 各段 `Content-Disposition`；文件段带 `filename` 与真实字节 |

> 所有 M 都必须在**运行态**验证（`buildContent()` 是惰性调用，编译通过 ≠ 功能正常）。沿用既有基线断言集，新增项追加到 `verify.cmd` 的探针里。

## 4. 核心机制：类型 → 编辑器

### 4.1 映射表

| 类型 | Content-Type | 编辑器 | 右端动作槽 |
|---|---|---|---|
| 无 | （不发送请求体） | 空态：`slash-circle` + 「本次请求不带请求体」；若内部仍保留上次 JSON，附一句「已保留 JSON 内容，切回即恢复」 | — |
| JSON | `application/json` | 等宽 `TextArea`，11 行 | `[格式化/压缩]` |
| **Form** | `application/x-www-form-urlencoded` | **键值表**：勾选 38 / KEY 弹性 / VALUE 弹性，尾行留空，5 行可见 | `[清空]` |
| **Form-data**（新增） | `multipart/form-data; boundary=…` | **键值表 + 逐行类型**：勾选 38 / KEY 216 / 类型 76 / VALUE 606（合计 936）。类型=文本 → 输入框；类型=文件 → `[选择文件] 路径 大小 [×]` | `[清空]` |
| XML | `application/xml` | 等宽 `TextArea`，11 行 | — |
| Text | `text/plain` | 等宽 `TextArea`，11 行 | — |
| **Binary**（新增） | `application/octet-stream` | 单文件选择器：`[选择文件]` + 路径 + 大小 + 清除；下方一行等宽元信息 | `[更换]` |

**为什么「类型」控件从 ComboBox 改成分段控件**：类型是**模式开关**而不是取值 —— 全部选项一眼可见、一次点击直达，不用经历「展开 → 找 → 选」。
分段控件 7 项，实测 `427.8 × 38`（轨道 38 = 项 32 + 内边距 3×2）。

**为什么右端是「动作槽」而不是固定按钮**：原实现里「格式化」按钮在非 JSON 类型下依然显示，点了没反应（D10）。
现在动作槽只放**当前类型真的可用**的动作，XML / Text 下槽为空。

### 4.2 逐类型内容保留（切换不丢数据）

每种类型的编辑内容**各自独立持有**，切换只换可见节点，不清空：

- `TextArea` 的文本：JSON / XML / Text 共用**同一个** `TextArea`（只换 promptText 与动作槽），避免「切到 XML 再切回来 JSON 没了」。
- `FORM` 的键值行、`FORM_DATA` 的行、`BINARY` 选择的文件：**各自独立的模型对象**，随页面生命周期持有。
- 切到 `NONE` 不清空任何模型，只把编辑区换成空态。

### 4.3 两条必须一起做的守卫（否则「支持文件」只是半个功能）

#### 守卫 ①　Content-Type 一致性（D5 的闭环）

请求头表里若已存在与当前类型冲突的 Content-Type，工具行右端由「等宽 Content-Type」切换为：
**⚠ 消息图标 + 「请求头里已设 Content-Type: application/json，与当前类型 Form 不一致，将按请求头发送」**。

**不自动改用户的头**（自己改了更难排查），只把事实说出来。
图标必须自绘 SVG（`Icons.of("alert-triangle", …)`），不用 emoji 与 Unicode 符号。

#### 守卫 ②　方法 × 请求体（D6 的闭环）

- `inferBodyType` 的静默推断**保留**（它防止「粘完 JSON 忘了改类型」），但必须**说出来**：
  类型 = 无 而编辑区有内容时，工具行右端显示「本次按 JSON 发送（类型选了『无』，编辑区有内容）」。
- `GET` / `DELETE` 下有非空请求体时给一条**信息级**提示 —— 实测 JDK 会真的把它发出去（`status=200`），
  服务端行为不可预期，所以提示但**不阻断**。

### 4.4 HttpEngine 侧的三件事

1. **Form 真编码**：`BodyPublishers.ofString` 之前对每个键值对做 RFC 3986 百分号编码，用 `&` / `=` 拼接。
   现状完全没有编码，与界面上「会自动编码」的文案直接矛盾（D3）。
2. **multipart 组包**：生成 boundary，逐段写 `--boundary` + `Content-Disposition: form-data; name="…"`（文件段再加 `filename="…"`）+ `Content-Type` + 空行 + 内容 + CRLF，结尾 `--boundary--`。
   文件内容走 `BodyPublishers.ofFile` 或按段拼 `ofByteArrays`。
3. **Binary**：`BodyPublishers.ofFile(path)`，`Content-Type` 默认 `application/octet-stream`。

## 7. `DESIGN.md` 不变量核对表

| 不变量 | 本设计如何满足 | 实施后的验证方式 |
|---|---|---|
| 一屏只有一处主色实底 | 只有 Send 是 `.button-primary`；选择文件 / 清空 / 格式化 / 展开编辑全部落次操作与紧凑档 | 离屏渲染后数 `#2563eb` 实底按钮数 = 1 |
| 一屏只有一个最大字级 23px | 仅详情页标题 | 扫所有 `Label` 的 `font-size`，最大值出现 1 次 |
| 控件高度只取既定档位 | 见 §5 | 量每个控件实际高度逐档比对，越档即红 |
| `pref` 与 `min` 成对 | 请求页签 312、响应页签保底 132、工具行 38、键值表 210、折叠条 46 全部成对写 | 沿用 `nav` 探针的「尺寸完整性」断言（实际高 ≥ pref 高） |
| 装不下只能滚动，不能压缩 | 820×560 展开配置态时出外层滚动条（溢出 203），控件一个都不压 | 820×560 下量控件实际高 vs pref 高 |
| 颜色永不是唯一线索 | 取消勾选的行：勾选框形状 + 整行转 `-dt-text-subtle`；Content-Type 冲突：自绘 warn 图标 + 整句文字；文件丢失：明写「文件不存在」 | 灰度截图里逐条确认仍可辨 |

## 8. 窄窗降级：820 × 560（最小窗口）

> 本节为**计算值**，未做逐像素验证 —— 报告时按未执行处理。

| 量 | 值 | 推导 |
|---|---|---|
| 可用内宽 | 494 | 820 − 侧边栏 267 − 竖滚动条 11 − 左右留白 48 |
| 面板可用高 | 395 | 560 − 详情页头 85 − chrome 80（16 + 48 + 16） |
| 配置态需要 | 598 | 76 + 14 + 312 + 14 + 36 + 14 + 132 |
| **溢出** | **203** | → 外层出现滚动条（**确认的取舍**，不是通过） |

### 降级动作（按顺序生效）

1. **窄窗默认进入查看态**：请求折叠为 46px → 46 + 14 + 36 + 14 + 132 = 242 ≤ 395，**首屏不出现滚动条**；用户点「展开编辑」才滚动。
2. **Body 工具行内宽 < 620 时隐藏 Content-Type 常驻后缀**（可从「请求详情」页签读到）；冲突提示保留，文案压缩为「warn 图标 + Content-Type 与类型不一致」。
3. **分段项横向内边距 12 → 10**（427.8 → ≈ 414），配合 28px 的清空按钮，工具行需 414 + 8 + 66 = 488 ≤ 494，满足。
4. **form-data 表最小必需宽 614**（38 + KEY 120 + 类型 76 + VALUE 380）→ 内宽 < 614 时表格**横向滚动，不压列宽**。与批处理页结果表的处置一致（最小必需宽 520 → 免横滚临界 ≈ 1155px）。
5. 请求行的地址输入框允许压到约 250px（方法 124 + Send 100 + 间距 16），输入框自身横向滚动。

## 9. 实施顺序（每阶段可独立验收）

拆成 6 个阶段，**每阶段结束都要跑运行态探针**，不允许一次性大改后统一调。

> 设计稿本身的数字（行高加总 = 763、标尺标签 = 实测行高、列宽合计 = 936、令牌 30/30 一致）已由 `verify-mockup.cmd` 在真实 Chrome 里逐条实测通过；
> 那条「标尺标签 vs 实测行高」的断言，正是用来防「改了行模板却忘了同步标尺」这类**光看源码发现不了**的错误。

### 阶段 1 · 骨架与预算（不动业务语义）

- `.module-body` padding 收紧；carryOver 按钮并入业务页签行；请求 `TabPane` 248 → 312。
- 响应工具行 50 → 36 并把 Body 页签内的 42px 工具条并进来。
- **验收**：`nav` + `httpsect` 探针；断言 chrome = 64、请求页签实际高 ≥ 312、响应页签实际高 ≥ 132、首屏无外层滚动条。

### 阶段 2 · Body 类型控件换成分段控件

- `ComboBox` → 分段控件；动作槽按类型显隐；说明行并入工具行。
- **验收**：新增断言「逐类型切换后，动作槽内子节点数」；反向验证（把动作槽恢复成恒显「格式化」应变红）。

### 阶段 3 · 类型 → 编辑器（本轮的核）

- 新增编辑器容器 + 逐类型节点；`FORM` 用 `KeyValueTable`；`NONE` 用 `UiKit.setDegraded` + 空态。
- **验收**：逐类型断言编辑器实际节点类名与可见性（**改前必须能重现「恒为 TextArea」的失败**）；断言键值表实际高 ≥ 210。

### 阶段 4 · 新增 `FORM_DATA` / `BINARY` / `PATCH` + HttpEngine 组包

- 枚举扩展；`HttpEngine` 的 form 编码 / multipart 组包 / binary 文件流。
- **验收**：起 `TinyHttpServer` 收真实 socket 请求，断言
  ① form 的 `城市=北京 上海` 被编码成 `%E5%9F%8E%E5%B8%82=%E5%8C%97%E4%BA%AC+%E4%B8%8A%E6%B5%B7` 这类百分号序列；
  ② multipart 请求体里能找到 `boundary`、`name="avatar"`、`filename=`、以及文件真实字节；
  ③ `GetContent-Type` 与所选类型一致（无手设头时）。
- **反向验证**：把编码那行注释掉，断言必须变红。

### 阶段 5 · 折叠查看态 + 两条守卫

- 46px 摘要条（含展开/重发）；Content-Type 冲突提示；`inferBodyType` 显式提示；GET + body 提示。
- **验收**：`fire()` Send 后断言
  ① 请求区实际高 = 46；
  ② 响应页签实际高 = 488、内容 ≥ 432；
  ③ 摘要条上的「重发」`fire()` 后请求数 +1；
  ④ 手设冲突 Content-Type 时提示文字可见且含实际冲突值；
  ⑤ 一屏 `#2563eb` 实底按钮数 = 1（配置态为 Send，查看态为重发）。

### 阶段 6 · 收尾

- 更新 `DESIGN.md`（记录本页新高度口径）、`ARCHITECTURE.md`（`FormDataTable` 落在 features/http 内）。
- 重跑全部探针，基线计数只增不减；`jar tf` 纯净度检查（不得出现 `FormDataTableTest` 之类）。

## 11. 风险与已知缺口（不许当成「已通过」）

1. **窄窗（820×560）全部数字是计算值**，未做逐像素验证。展开配置态时外层必然出现约 203px 滚动条。
2. **form-data 表在窄窗下必然横向滚动**。
3. **若侧边栏不折叠，820 下内容区只有 553px** —— 这是本设计最紧的一档（`DESIGN.md` 已识别「侧边栏未实现折叠」为风险）。
4. **multipart 的 `filename` 与 `Content-Type` 推断**：按扩展名猜 MIME 只做最小映射（`.png` / `.jpg` / `.pdf` / `.json` / `.txt`），其余一律 `application/octet-stream`。不做完整 MIME 表。
5. **大文件**：`Binary` 与 form-data 的文件段目前整份读进内存（`BodyPublishers.ofFile` 已是流式，但 multipart 组包按段拼字节数组会是全量）。
   超过约 100MB 的文件未做流式分段 —— 记录为已知限制，本轮不做。
6. **JDK `HttpClient` 对 GET + body 不报错**，会真的发出去。本设计只提示不阻断（D6）。
7. **设计稿 §13 的实测口径**：`(表高 − 表头) ÷ 34` 与历史探针一致；`.kvrow` 在浏览器里实测 33.2px 是 1px 边框 + 1px 内边距被 flex 平摊所致，行的设计值仍是 34。

### 12.1 实施中实测出的两处预算漏项（本设计的账算漏了）

### 12.2 一处按设计意图补的实现细节

§3.2 要求「按下 Send 的瞬间折叠，让『请求中…』直接出现在被放大的响应区里」。
