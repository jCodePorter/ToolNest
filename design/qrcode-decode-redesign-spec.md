## 2. 实现细节

### 2.1 批注 A：动作行并入页签行 —— 两种做法与取舍

**问题**：`openBtn / pasteBtn / decodeClearSelBtn` 现在位于 `leftBox` 内，是**解析页签的内容**。
要「移到页签行右端」，页签行是 `TabPane` 自带的 Tab 头区域 —— **`TabPane` 的 Tab 头不接受外部节点**，
不能把三个按钮塞进 `.tab-header-area`。因此只有两条路：

#### 做法甲（**本稿采用**）：`TabPane` 与动作行做成同级 HBox

```
bizrow = new HBox(segTrack, UiKit.spacer(), actrow)   // actrow = HBox(openBtn, pasteBtn, decodeClearSelBtn)
VBox page = new VBox(bizrow, tabPane);
```

- **优点**：改动最小、最稳。页签仍由 `TabPane` 原生管理（选中态、键盘左右切换、`:focused` 都白拿）。
- **代价**：`bizrow` 与 `tabPane` 的 Tab 头**是两个独立布局带**，必须靠**显式高度对齐**才能视觉上「同处一行」。
  实测：页签滑块纵向带 `y ∈ [107, 145]`（高 38），动作行 `y ∈ [110, 142]`（高 32），
  即**动作行在页签带内垂直居中**（上下各留 3px）。这个 3px 不是巧合 ——
  `bizrow` 高 64 = 上留白 16 + 页签带 38 + 下留白 10，动作行靠 `Pos.CENTER_LEFT` 落在页签带中央。
- **风险点**：一旦页签标签文案变长导致 Tab 头变高，`bizrow` 的 64 与 `SplitPane` 的 613 都要重算。
  → 所以 `bizrow.setPrefHeight(64)` 与 `.seg` 的 `-fx-pref-height: 38` **必须成对维护**。

#### 做法乙（**不采用**）：把页签整体换成自绘 ToggleGroup

- 用一个 `HBox` + `ToggleGroup` 自绘「胶囊页签 + 右端动作行」，彻底摆脱 `TabPane` 的 Tab 头约束，
  一行之内想放什么放什么。
- **优点**：语义自由，未来页签行右端要挂更多东西不受限。
- **不采用的代价**：① 要自实现 Tab 的键盘导航（左右箭头切换 + 焦点环），容易漏；
  ② 与项目里**其它所有模块**（HTTP 单一请求页、文本对比页）的页签订位不再一致，
  设计系统的一致性成本高于本条收益。
- **结论**：**甲**。仅当后续有第二个模块也要「页签行右端挂动作」时，才值得把甲抽象成 `UiKit.tabRow(...)` 统一封装。

> **给实现者的硬提醒**：做法甲里，动作行**不是** `TabPane` 的子节点，所以它**不随页签切换隐藏**。
> 本页只有「解析 / 生成」两个页签，而三个动作**只属于解析页**（生成页有自己的输入）。
> 因此实现时**必须在 `selectedItemProperty` 监听里显式 `actrow.setVisible/setManaged` 跟随解析页签** ——
> 这是一处极易遗漏的**运行态**缺陷：编译一定通过，但切到生成页签后按钮仍留在原地。
> 对应探针断言见 §4。

### 2.2 批注 B：右栏底部按钮行删除、动作下移到卡片

删除 `rightBox` 底部的 `buttonRow`。其三个动作的去处：

| 原动作 | 新去处 | 实现 |
|---|---|---|
| `copyBtn`（复制结果） | 每张结果卡片头部「复制」 | 卡片头三段 HBox 的第二段；`UiKit.copyButton` 语义不变，但**复制的源**从「全部结果」改为**该卡片的文本** |
| `openUrlBtn`（在浏览器打开） | 每张结果卡片头部「打开」 | 同上；仅当该卡片内容是网址时可点（否则 `setDisable(true)`，沿用现有 tooltip 文案） |
| `clearBtn`（清空） | **页签行右端第 4 位**，改名「移除图片」 | 见 §2.3 |

**语义变化，必须在提交信息里写明**：改造前页面级「复制结果」只能复制**全部**
（`allResultsText()`）；改造后每张卡片独立复制。若产品仍需要「复制全部」，
在结果区标题行「识别结果 + 计数」旁**再加一个静默动作「复制全部」**（本稿未画，留待 Q5）——
但注意那会让「结果区标题行内不含任何可点控件」这条结论失效（见 §5-Q5）。

**卡片头布局**：三段 = 序号徽标 `#n`（14.1px）+ 格式徽标（57.1px）+ 动作组（124px）。
实测三段合计 **195.2px ≪ 头行内宽 423px**，右侧是弹性的 —— 动作组应 `HBox.setHgrow(spacer, always)`
把动作推到最右，而不是让三段均分。

### 2.3 批注 C：清空的落点 —— **已确认：改名「移除图片」，接到页签行右端**

**你的确认**：清空清的是**图片**（连同结果一起回空态）。因此它与「选择图片／粘贴剪贴板／清除框选」
同属「对**图**做操作」一类，落在**页签行右端第 4 位**，而非结果区标题行。

落地口径：

```
actrow = HBox(openBtn, pasteBtn, decodeClearSelBtn, actsep, removeImgBtn)
//   ↑ 三个「取输入」              ↑1px 竖线  ↑「丢弃」一个
```

- **改名**：`clearBtn` → 「**移除图片**」。把「清的是图」写进按钮文案，消除「是不是只清结果」的歧义。
  （方法名 `clearDecode()` 可保留，它的行为本来就是「清图 + 清结果」，与新文案一致。）
- **形态**：由 `dangerButton` 降为 `quietButton` + 图标（图标+文字内联形态，见 §2.5）。
  **高度取 32**，与同行三个邻居齐高 —— 它落在 48px 页签行（页签带 38）内，本就有 32px 的落位空间，
  不要因为「它不占控件档位」就压到 24 或按文字行高渲染，那会让一行内高度参差。
- **分隔线**：`Region` 1×18，`-fx-background-color: -dt-border-strong`，放在第 3、4 个按钮之间。
  作用是让「取输入（3 个）」与「丢弃（1 个）」两组**在视觉上分层**，避免 4 个按钮糊成一排。
  实现时用 `HBox` 的 `spacing` 会给它两侧各 8px，比手工 margin 稳。
- **降级**：无图时 `UiKit.setDegraded(removeImgBtn, note, true)`，**不隐藏**，位置固定
  （符合「动作不随状态出现/消失」的约定 —— 这也是批注 A 把动作固定到页签行的用意）。
- **结果区标题行**：右端改放**只读**的汇总说明（「共 N 个二维码」），**不含任何可点控件**。
  断言：`.rhead .btn` 数量 == 0。

**宽度核算（实测）**：4 个按钮合计 502.5px（含 3 个 8px 间距 + 1 个分隔线），
页签行可用带 702px，**余量 199.5px**。空间充裕，不需要为了塞下第 4 个按钮而缩小任何一个。

### 2.4 提示条（`decodeNotice`）出现时，结果列表让位算法

标题行引入后，右栏变为 **标题行 32 + 间距 8 + 列表(弹性) + 提示条(弹性出现)**。
由于 `decodeNotice` 是**按需出现**（错误/警告就近内联），必须约束「它出现时谁让位」：

```
规则（自上而下优先级）：
1. decodeNotice 一旦 visible，先取自己所需高度（单行提示 28，双行 46）。
2. 结果列表 resultScroll 的 minHeight 压到「2 张卡高 + 1 个间距」= 74.75*2 + 10 = 159.5，
   表达「至少要露出两张卡，否则用户不知道有结果」。
3. 剩余高度全给 resultScroll 的 maxHeight。
4. 若「标题 32 + 8 + 列表 min 159.5 + 提示 46 > 613」，则提示条**允许把列表压到 2 张卡以下**——
   因为错误信息不可省略。此时列表进入内层滚动。
```

实现要点：
- `resultScroll.setMinHeight(159.5)`、`setMaxHeight(Double.MAX_VALUE)`、`VBox.setVgrow(resultScroll, ALWAYS)` —— **三件套缺一不可**
  （见项目记忆：只设 `Vgrow` 会静默失效）。
- `decodeNotice` 用 `setManaged(false)` 收起时**必须同时 `setVisible(false)`**，否则占位仍在。
- 复用 `UiKit.showNotice / hideNotice`，不要自己写 `setVisible`。

### 2.5 图标可用性核查（对实现者的硬事实）

设计稿里出现了「复制」「打开」「移除图片」三个**图标 + 文字**的行内动作。核对 `Icons.java` 现状：

| 图标名 | 是否已注册 | 说明 |
|---|---|---|
| `copy` | ✅ 有 | 可直接用 |
| `external` | ✅ 有 | 即「在浏览器打开」的外部链接图标 |
| `trash` | ❌ **没有** | 全项目 grep `trash` 命中 **0** |
| `x` | ✅ 有 | 是「关闭」语义，**不等于「移除图片」** |

**结论（已确认形态为图标+文字，所以这是必须项）**：需要**先在 `Icons.java` 的 `PATHS` 里新增 `trash` 图标**
（24 网格、圆头圆角、单描边公式，风格照抄现有 `copy`/`x`）。设计稿里用的 path 可直接搬：

```
Map.entry("trash", "M4.5 7h15M9 7V5h6v2M6.5 7l1 13h9l1-13")
```

**不要**用 `x` 替代（它语义是「关闭」，会让人误解为「关闭结果区」）。

**共享构件取舍（`UiKit.linkAction`）**：本轮需要的「图标 + 文字、无底无框」行内动作，
在两个地方出现（页签行的「移除图片」、卡片头的「复制 / 打开」），形态一致 —— 具备抽象价值。
两条路：

- **甲（推荐）**：在 `UiKit` 新增 `linkAction(String iconName, String text, Runnable action)`，
  返回一个 `Button`，styleClass 为 `link-action`，在 `app.css` 里定义（`transparent` 底、
  无边框、主色文字、`-fx-padding: 0 8`）。**风险**：这是**全站共享工厂方法**，
  一旦命名/样式定下就被其它页复用，属于本轮唯一的外溢面。
- **乙**：只在 `QrModule` 内私有实现（`private Button linkAction(...)`）。
  零外溢，但与未来其它页的同形态动作会各写一遍。

**建议乙先落地、甲留待第二处使用时再抽**（避免为一个页面的需求过早定公共契约）。

> 另注：`QrModule.java` **目前完全没有 import `Icons`** —— 整个解析/生成页的按钮都是纯文字。
> 本轮若引入图标，是**该模块第一次用图标族**，属于新的一致性基准，需在提交信息中注明。

## 3. 不变量自检（对应设计稿 §10）

| 不变量 | 本稿判定 | 依据 |
|---|---|---|
| 溢出时不允许压缩 | 通过 | 预览框吃剩余高度但 `minHeight` 保住 2 张卡；见 §2.4 |
| 仅一种主色实底 | 通过 | 画布内主色实底按钮 **0**（本页无提交动作） |
| 必须标注单位 | 通过 | 面积预算表全部标 px |
| 控件高度四档（32/36/30/28） | 通过 | 页签行 4 个动作 **32**；卡片内动作 **28**；不再出现越档的 24px |
| 按钮四档语义 | 通过 | 「移除图片」由 `danger` 降为 `quiet` 后，全页无破坏色按钮 |
| 状态切换不改尺寸 | 通过 | 「移除图片」置灰只改色与不透明度，尺寸恒 32 |
| 页签双层结构（外胶囊 + 内下划线） | 保留 | 本稿不放宽页签视觉，只改「页签行右端可挂动作」 |
| 空态 | 保留 | 见设计稿 Fig2；左栏虚线拖放区 565 高 |

### 4.1 ⚠ 必须同步修改的既有断言（本轮唯一破坏性改动）

`verify/.../qrcode/MultiQrProbe.java` 现有两条断言在 Q2 定案后**不再成立**：

| 位置 | 现有断言 | 为什么失效 | 改为 |
|---|---|---|---|
| 第 115–117 行 | `module.resultCardCountForTest() == decoded.size()`（"界面卡片数 == 解码条数（第 2 个码没有被丢弃）"） | 9 个结果只画 6 张卡 | `resultCardCountForTest() == Math.min(decoded.size(), 6)` |

### 5.1 Q2 的实现要点（只展示 6 张整）

- 列表容器高维持 **573**（= 右栏 613 − 标题行 32 − 间距 8），**不要**为了「刚好装 6 张」把它压到 498.5 ——
  那会让列表高随内容变化，与既有的「列表 `VGrow` 吃剩余」逻辑冲突。

## 6. 放弃的替代方案（备查）

- **把动作行做成 `TabPane` 的 `graphic`**：`Tab` 的 graphic 只能承载单个节点，且会被 `Tab` 的选中态
  裁剪效果影响（亚特兰大主题下 graphic 参与文本省略计算），不可行。
- **把动作做成 ToolBar 停靠在窗顶**：脱离「取输入动作就近图片」的语义，用户要多一次视线跳转，否决。
- **卡片正文压到 0 行换取 10 张可见**：长网址完全不可见 —— 而本页存在的意义就是核对网址，否决（设计稿 Q2-c）。
- **把「移除图片」放结果区标题行**（早前版本的方案）：**已被你的确认否决** ——
  它清的是图，挂在结果区会让人误以为只清结果。保留在此备查。
- **「移除图片」压到 24px 或按文字行高渲染**：与「图标+文字不占控件档位」的说法自洽，
  但会让同一行内四个动作高度参差（32 / 24 混排），否决；统一取 32。
