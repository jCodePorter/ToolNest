# HTTP 批处理页 · 备选版式评估（候选对比）

- **模块**：`网络请求类工具 / HTTP 请求工具 / 批处理`
- **版本**：v1（评估稿，非实现稿；**不改动**已冻结的 `http-batch-redesign.html` 与 `http-batch-redesign-spec.md` v5）
- **评审口径**：窗口 **1266 × 763**（验收尺寸）；侧边栏 268 → 内容区 998 → 减左右留白 48 → **可用宽 950**
- **本轮触发**：用户提出替代版式「横向三块：配置 / CSV 输入 / 执行配置 + 执行结果」
- **纪律**：所有结论落在算术上，不写「看起来更宽敞」。

## 4. 逐候选：成立条件 / 收益 / 代价

### V1 · 横向三栏等宽（用户提案的直接读法）

- **成立条件**：窗口 ≥ **1904px**（≈ 3 × 520 + 两间距 + 留白 + 侧边栏）。1266 下**不成立**。
- **收益**：三块信息一屏并列，视线不用上下跳；竖向不再切分，结果表可拿到 11 行。
- **代价（算术）**：
  - 结果表可用 307 < 520 → **横向滚动 213px**，`地址` 与 `响应预览` 被推出视口（回滚才能看）；
  - 请求行 URL 只剩 **149px**（`http://localhost:8999/user/{id}` 连占位符都显示不全）；
  - 执行条 275 < 429 → 被迫 **3 行（124px）**；
  - CSV 预览表 275 → 多列必然横滚。
  - **本质**：纵向压力被搬到了横向，一屏内「能看见」的信息总量反而下降。

### V2 · 两栏（左＝请求模板 + CSV 叠，右＝执行配置 + 结果叠）

- **成立条件**：窗口 ≥ **1370px**。1266 下**不成立**（差 52px）。
- **收益**：输入与结果各占一栏，右键连续跑批时视线固定，不用上下跳。
- **代价（算术）**：
  - 右栏 468 < 520 → 结果表 **横向滚动 52px**（`响应预览` 尾部被切）；
  - 执行条在右栏卡内 436，行 2 需 429 → **余量仅 7px**，任何标签变长即破；
  - CSV 预览表 436（与现状同级）。
  - **修正主理人参考值**：参考值称「左栏两张卡各需 ≈300、挤压请求体与 CSV 预览」——**在 763 高度下不成立**：左栏 653 = 请求模板 252 + 间距 12 + CSV 389，两张卡合计 512 ≤ 653，**无挤压**，CSV 预览反而拿到 389 − 128 = 261px（≈6 行）。此条**只在窗口高 < ~640px** 时才成立。

### V3 · 现状基准（上输入双栏 + 下结果整宽）—— 引用 v5

- **成立条件**：窗口 ≥ **1252**（综合）。
- **收益**：结果表 589 ≥ 520 **不横滚**（余 69px）；输入两块同屏可编辑；已验证（QA 24 条 PASS）。
- **代价（算术）**：配置态结果区 **301px** → 表 **6 行**、详情 **11 行**；要更大的结果区只能折叠输入区（运行态可到 15 / 25 行）。

### V4 · 输入区内层页签（整宽 950）+ 结果区吃剩余高度

- **成立条件**：窗口 ≥ **1155**（四项里最低）。
- **收益（算术）**：
  - 结果区 341px（比 V3 多 **40px**）→ 表 **7 行**、详情 **13 行**；
  - 执行条整宽 918 ≥ 664 → **回到单行 36px**（相对两行省 44px）；叠加「卡头条 34 → 页签条 30（−4）」与「新增一条间距（+8）」，**净省 40px** —— 正是结果区多出的那 40px（340 → 300）；
  - CSV 预览表整宽 918 → 多列不横滚，行数也从 5 行 → **6 行**；
  - 结果表 589 ≥ 520，仍不横滚。
- **代价**：
  - **输入两块不能同屏**：请求模板与 CSV 数据需点击切换（配置态看不到「模板 + CSV 预览」并排的对照关系）；
  - 多一次点击；若用户习惯「边看 CSV 表头边改占位符」，此方案会打断。
- **输入区 300px 的精确构成**（可复核）：`内边距 16 + 内层页签条 30 + 间距 8 + 请求行 36 + 间距 8 + 请求体类型行 32 + 间距 8 + 请求体 64 + 间距 8 + 请求头 30 + 间距 8 + 执行条（单行）36 + 内边距 16 = 300`。

### V5 · 宽屏三栏 1fr / 1fr / 1.6fr

- **成立条件**：窗口 ≥ **1514**（结果表不横滚）／≥ **1993**（URL ≥ 300 舒适）。1920 全屏下 438 / 438 / **700**。
- **收益**：结果栏 700 ≥ 520（余 180）；执行条回到单行；纵向结果区可到 22 行（@1080 高）。
- **代价（算术）**：
  - **URL 是真正的瓶颈**：@1920 栏 1 = 438 → 卡内 406 → URL **280 < 300**；要到 300 需窗口 **≥ 1993**。也就是说 V5 在 1920 下「结果表很舒服、请求模板却偏窄」；
  - 需新增断点 1514／1993，只有超宽屏才有意义；笔记本（1366×768 / 1440×900）**落在阈值以下**，会退化成 V1 的横滚问题。

## 5. 为什么结果区必须整宽

**520px 的来历（全是不能压的算术）**

| 列 | 宽 | 依据 |
|---|---|---|
| `#` | 40 | 三位以内序号 + 内边距 |
| `状态` | **62** | 「等待中」= 12.5 × 3 = 37.5 + 内边距 20 = **57.5** → 取 62。**56px 会截断成「等待…」**（本项为验收已抓到的真实缺陷） |
| `耗时` | 68 | 「99999 ms」 |
| `地址` | min **150** | 弹性列下限（长 URL 靠 tooltip 兜底） |
| `响应预览` | min **200** | 弹性列下限（约 16 个汉字） |

**定宽 170 + 弹性下限 350 = 520px** —— 这是「一眼能核对一行结果」的最低信息量。

**把结果区压窄 ≠ 让版面变松**
- 结果区整宽 950 时：分栏左栏 589 ≥ 520 → 表**不需要**横向滚动，横向空间是**够的**。
- 一旦把结果区切成 307（V1）或 468（V2）：表**必横滚** 213px / 52px → `地址` 与 `响应预览` 移出视口。
- 结论：**横向与纵向是同一笔预算的两端**。结果区变窄，只是把「纵向看不见的行」换成「横向看不见的列」；而表格的横向滚动比纵向滚动更难用（列头随之滚走，从此不知道哪列是哪列）。

**因此**：结果区应当永远占**整幅内容宽**（950），「省纵向」要靠在**输入区**做折叠/页签，而不是靠切窄结果区。

## 6. 推荐

| 场景 | 推荐 | 理由 |
|---|---|---|
| **1266×763（验收尺寸，日常窗口）** | **V4**（用户若能接受输入区页签切换）<br>否则保持 **V3** | V4 在同一宽度下把结果区从 301 → **341px**（6→**7** 行、11→**13** 行），并让执行条回到单行、CSV 预览整宽不横滚；**代价只是输入区多一次点击**。V3 仍是「两块输入同屏」唯一不横滚的版式，是稳妥基线。 |
| **宽屏 ≥ 1514（建议断点 1920）** | **V5** | 三栏并列、结果栏 700 不横滚、执行条单行；但需注意 URL 在 1920 下只有 280px，若在意请求模板宽度，宜把比例从 1/1/1.6 调成 **1.2/1/1.4**（栏 1 变大、结果栏仍 ≥ 520）。 |
| **窗口 < 1155** | 沿用 V3/V4 的**降级口径** | 结果表横滚、不压列宽（v5 §4.4.1 已定）。 |

> **不推荐 V1 / V2**：它们把结果区压到 307 / 468，直接违反「结果表 ≥ 520」这条硬尺子，在验收尺寸上就会横滚。

## 9. 决策记录（用户最终裁定）

**裁定：采用「纵向三段式 + 前两段执行时自动折叠」。** 落地在 `design/http-batch-redesign-spec.md` **v6**。

**用户原话**
- 「我打算改成纵向三段式，第一段配置，第二段 csv，第三段执行配置与结果。其中第一，第二在执行时可以自动折叠」
- 「我想要实现这种排版，纵向可以增加滚动条」
- 草图：一个外框内**自上而下三个方框** —— ① 请求模板区 ② CSV 解析区 ③ 执行配置和结果区，右侧画了纵向滚动条。

### 三段式不是 V1–V5 中的任何一个

V1 是**三栏等宽（横向）**、V5 是**宽屏三栏（横向）**；用户选的是**纵向堆叠**的三段。它同时解决了本文件发现的两个硬约束：

| 本文件发现的约束 | 三段式如何解决 |
|---|---|
| **执行条 436px 卡内边界**（§1、§4：双栏下请求模板卡内只有 436，单行需 664，被迫拆两行） | 三段各占**整宽 950（卡内 918）** → `664 ≤ 918` ✓ → **执行条回到单行 36px**；请求行 URL 从 310 → **792** |
| **结果区必须整宽**（§5：结果表最小必需宽 520，窄了就横滚） | 结果区仍在段 ③ 内占整宽，分栏左栏 `0.62 × 950 = 589 ≥ 520` ✓ → **不需要任何横向滚动** |

### V1–V5 的评估结论**存档保留**

它们解释了两条至今仍然成立的约束，v6 是**绕开**而非推翻：
- **为什么不是三栏**（§4 V1）：V1 每栏 307 → 结果表缺 213px、URL 仅 149px。横向分栏的结论不变 —— v6 的三段是**纵向**的，每段仍是整宽。
- **为什么结果区必须整宽**（§5）：520 = 170 定宽 + 350 弹性下限；压窄结果区只是把「纵向被压」换成「横向被压」。v6 完全遵守这条。

### 关键数字（v6，1266 × 763）

| 项 | 配置态（三段全展开） | 运行态（段①②折叠） |
|---|---|---|
| 段 ① / ② / ③ | 252 / 300 / 345 | 46 / 46 / 537 |
| 内容总高 vs 视口可用 653 | **921** → 外层滚动 **268px** | **763**，无滚动 |
| 结果表可见行数 | 6 行（需滚动到段 ③） | **13 行** |
| 详情可见行数 | 11 行（需滚动） | **22 行** |
| 结果表可用宽 | 589 ≥ 520，不横滚 | 同 |

### 相对本文件推荐的变化

本文件推荐「1266 用 **V4**（输入区内层页签）」—— **已被用户否决**。原因：V4 的三项收益（结果区 +40px、执行条回单行、CSV 整宽），三段式以**更高幅度**同时拿到（运行态结果区 537 → 13 行、执行条单行、CSV 预览整宽 918），而代价从「输入两块不能同屏、切换需点击」变为「配置态需下滚 268px」—— 用户已明确接受纵向滚动。

> 一句话：**V4 是「在两栏里省出 40px」，三段式是「把每段拉成整宽、把纵向压力交给滚动条」；后者同时解开了横向与纵向两处死结。**
