01诊断：为什么现在「粗糙」

一句话结论：请求体区把 5 种语义完全不同的请求体压在了同一个 TextArea 上 —— 那个「类型」下拉只改变编辑区的不透明度，不改变编辑器的形态。于是 Form 只能手写 a=1&b=2（而且并不编码），文件上传则根本不存在。

探针把这句话量成了事实：逐个选中 5 种类型，Body 页签内 TableView 数量恒为 0、TextArea 数量恒为 1， 不透明度只有 NONE 一档从 1.00 变 0.42。也就是说除「变淡」以外，切换类型没有产生任何界面变化。

03核心改动：类型 → 编辑器

「类型」是一个模式开关，不是取值 —— 所以它从下拉框改成分段控件：全部选项一眼可见、一次点击直达、 不用经历「展开 → 找 → 选」。右端留一个固定宽度的动作槽，只放当前类型真的可用的动作（这是 D10 的反面：不给假按钮）。 槽左侧常驻实际会发出去的 Content-Type，等宽小字 —— 比起让用户切到「请求详情」页签里翻，把它放在类型旁边才有用。

3.1 两条必须一起做的守卫（否则「支持文件」只是半个功能）

守卫 ①　Content-Type 一致性

请求头表里若已存在与当前类型冲突的 Content-Type，工具行右端由「等宽 Content-Type」切换为 请求头里已设 Content-Type: application/json，与当前类型 Form 不一致，将按请求头发送。 不自动改用户的头（自己改了更难排查），只把事实说出来。这是 D5 的闭环。

守卫 ②　方法 × 请求体

当前实现里 inferBodyType 会在「类型=无 但编辑区有内容」时静默按内容形状改类型再发出去。 静默推断要保留（它是防止「粘完 JSON 忘了改下拉框」的安全网），但必须说出来：工具行右端显示 本次按 JSON 发送（类型选了「无」，编辑区有内容）。同理，GET 下有非空请求体时给一条信息级提示 —— 实测 JDK 会真的把它发出去，服务端行为不可预期，所以提示但不阻断。

Q1　请求区什么时候折叠？
  • 选项 A（推荐）：按下 Send 即折叠。响应区立刻从 132 → 488，连「请求中…」都在大区域里显示。
  • 选项 B：不自动折叠，只在摘要条位置给一个「最大化响应区」按钮，用户自己点。
  • 选项 C：折叠开关持久化到配置，用户自己选默认行为。

倾向 A：批处理页已经确立了「配置折叠、结果常驻」的语言，同一模块里保持一致比单页最优更重要。

Q2　折叠之后想改一个参数再发，走哪条路？
  • 选项 A（推荐）：点摘要条上的「展开编辑」→ 完整配置回来。
  • 选项 B（已并入主设计）：摘要条上直接放「重发」，不展开也能重试。
  • 选项 C：两条都给。
Q3　新增的 Form-data / Binary 进不进批处理页？（影响面最大的一条）

批处理页用 {列名} 占位符把 CSV 的值替换进请求。文件字段没有「值」可言，只有路径 —— 于是必须先定义：CSV 里的一列能不能直接写成文件路径？

  • 选项 A（推荐）：本轮只做单一请求页。批处理页暂不暴露 Form-data / Binary（枚举扩了，但批处理页的类型下拉先不列出来），单独一轮再设计文件列的占位符语义。
  • 选项 B：同时支持，占位符 {文件名} 指向 CSV 里的路径，路径不存在就按行记失败。
  • 选项 C：同时支持，但文件列只允许「一整列都是同一目录下的文件名」这种受限形态。
Q4　方法要不要补齐？
  • 选项 A（推荐）：补 PATCH（接口调试的高频缺口）。
  • 选项 B：补 PATCH + HEAD + OPTIONS。HEAD 无响应体，响应区需要一句专门的说明；OPTIONS 返回头信息，现有「响应头」页签够用。
  • 选项 C：再加「自定义方法」输入框（JDK 的 method(name, publisher) 支持任意方法名）。
Q5　Params 的 DESCRIPTION 列怎么处置？
  • 选项 A（推荐）：删除。它现在恒空且点不进字，是纯占位；245px 还给 KEY / VALUE 立刻可见。
  • 选项 B：做成真正可编辑并参与保存（Postman 有这列）—— 那是新功能，需要独立的范围与验证。
  • 选项 C：只保留在 Params，Headers / Form 不加。
Q6　Content-Type 冲突的默认处置？
  • 选项 A（推荐）：只提示，不改用户的头。事实是「将按请求头发送」，说出来即可。
  • 选项 B：切换 Body 类型时自动覆盖请求头里的 Content-Type（更省事，但用户可能故意设过）。
  • 选项 C：弹一次确认，让用户当场选。
Q7　详情页头那 85px（含独立面包屑行）动不动？

把面包屑并到标题行右侧可再省约 20px，但这会改动 UiKit.pageHeader，影响全部 11 个详情页，不在本轮范围内。 本轮 chrome 只动 HTTP 模块自己的部分（业务页签行与卡片间距）。要不要单开一轮统一收壳？
