## 修 HTTP 单一请求页三个实测缺陷 + Form/Form-data 合并

### 三个缺陷的根因（都是同一处）
`KeyValueTable` 用 `TextFieldTableCell` —— 它是「按下编辑 → 改完提交」模型，
**编辑期间行模型还是旧值（通常是空串）**。由此串出三条：

1. **「+ JSON」输出 5 行**：`setEntries` 逐条 `add`，每条都触发监听器里的
   `ensureTrailingBlank()`，再叠上末尾两行显式 `add(new Row(""))`
   → Content-Type + 4 空行。`clear()` 同样是 `setAll` 两行。
2. **输入后失焦 / 内容消失 / 加不上行**：
   - `setOnKeyTyped` 里判断「末行是不是空行」读的是**未提交的空模型**
     → 永远得到「是空行」→ **永远不补行**（加不上参数）
   - 一旦提交，`onEditCommit` 改模型又触发补行，**`ObservableList` 增删让
     `TableView` 重建单元格 → 正在编辑的编辑器连同未提交的文字一起被销毁**
     → 失焦 + 内容消失
3. `FormDataTable` 的 KEY 列同病（VALUE 列已经是常驻 TextField，没问题）。

### 修法
- **换成常驻 TextField**（graphic，不是 editor）：打字即写通行模型，没有「提交」这一步。
  `table.setEditable(false)`（留着 editable 会让点击额外弹一层编辑器与常驻框抢焦点）。
  三条同时消失。`FormDataTable.ValueCell` 原先每次 `updateItem` 都 `new TextField`
  —— 也要改成复用，否则「补一行空白行」引起的重布局同样会换掉正在输入的框。
- **补行改异步**：`Platform.runLater` 排「发现末行有内容 → 补一行」。
  绝不能在按键事件里改列表。
- **批量替换用 `bulkEdit` 静音 + 一次 `setAll`**：在 `ObservableList` 自己的
  变更回调里再改这个列表是重入操作。
- 不变式：**末尾恰好一行空白行**（`clear()` 后是 1 行，不是 2 行）。

### Form 与 Form-data 合并（按 Postman 截图）
两个类型选项、**共用同一张表**，区别只是「行里能不能选文件」：
- `editorFor(FORM)` 与 `editorFor(FORM_DATA)` 都返回 `formDataTable`；删掉 `formTable`
- `setFileRowsAllowed(boolean)`：Form 隐藏「类型」列并把已有文件段落回文本段
  （`x-www-form-urlencoded` 传不了文件，但保留 `path`，切回去还能看到）
- 内容始终是同一份，来回切不丢
- `currentSpec()`：Form 收 `formEntries()`（键值对，引擎负责百分号编码），
  Form-data 收 `fields()`（逐段模型）—— 两种模型不混用
- 动作槽新增「+ 新增字段」；Params/Headers 工具行新增「+ 新增参数」「+ 新增请求头」

### 踩到的坑
- **`addRow()` 不能复用 `appendTrailingBlank()`**：后者是「保证末行是空的」，
  末行本来就空时**什么都不做** → 空表上点「+ 新增参数」毫无反应。
  「+ 新增」要的是「多给我一行」。这条是探针先红才发现的。
- **`TableView.getRow(int)` / `TableRow.getCell(int)` 不是公开 API**，
  编译不过。只能 `table.lookupAll(".table-row-cell")` 顺场景图数行/列。
- **`getTableRow()` 在外层类里调不到**（它是 `TableCell` 的方法）→ 每个 cell
  内部自己写一个 `currentRow()`。
- **无头环境断言 `isFocused()` 是恒假的**（Headers 页签不可见，requestFocus 拿不到焦点）。
  恒假断言比没有断言更危险。改成断言「补行后正在输入的那一格还是**同一个节点**」——
  这正是「内容消失」的机制本身，稳定可测。
- **探针在 FX 线程上不能用 latch 等 `runLater` 排空**（把自己锁死，实测 10s 超时）。
  改用 `flushPendingAppendForTest()` 同步执行同一段逻辑 —— 对焦点反而是**更严**的考验。
- 字段初始化顺序：`kindCol = kindColumn()` 写在 `table` 之后（cellFactory 里要用 `table`）。
- `setTextFieldsForTest` 要**插在尾部空行之前**（`rows.add(size-1, ...)`），
  直接 `add` 会排到空行后面，表首多一个空行，后面按行号取值的断言全错位。

## 追加：「+ Token」快捷按钮（Headers 工具行）

在 `+ JSON` 旁边加 `+ Token`，落一行 `Authorization`，值做 Bearer 前缀处理。

### Bearer 判据不能只查「含不含 Bearer」
用户原话是「如果添加有 Bearer 就无需处理，否则拼接 Bearer」。字面实现
（`contains("Bearer")`）会错：`Basic dXNlcjpwYXNz` 不含 "Bearer"，
于是被改成 `Bearer Basic dXNlcjpwYXNz` —— **把一条能用的头改坏**。
`Authorization` 的 scheme 是 HTTP 的 token（Basic/Bearer/Digest/Token...），不是只有 Bearer。

正确判据两步：
1. **整串没有空白 → 它就是一个裸 token**（JWT 形如 `aaa.bbb.ccc`）→ 直接补前缀。
   第一步不能省：JWT 里全是 `.` `_` `-`，都是 scheme 合法字符，
   只按「首段是否合法」判会把整个 JWT 误当成一个 scheme 而**漏掉前缀**（我第一版就错在这）。
2. 有空白 → 看首段是否合法 scheme（RFC 7235 token：首字符字母，其余字母数字与 `-._~+/`）。
   有就原样返回，没有才补。

### 必须按 key 分派
规范化器签名是 `(key, value) -> value`，**只对 `Authorization` 生效**。
无差别套用会把 `Content-Type: application/json`（也没有空白）改成
`Bearer application/json`。

### 规范化跑在两处
- **失焦时**（`focusedProperty` 监听）：给即时反馈。**不能在按键时做** ——
  边打边改会把用户刚敲的字符顶走（「b」变「Bearer b」）。
- **取值时**（`entries()`）：兜住「粘完直接点 Send」。失焦只在焦点真的离开过
  那一格时才跑得过，而 `entries()` 是**一定会**发生的那一刻（Send / 导出 / 存模板都走它）。
  **取值路径不写回模型** —— 只影响发出去的值，表格里显示的仍是用户敲的原文。

### 落位语义
`addEntry(key, value, transform)` 三段式，**不堆行**（反复点不会堆出多条
Authorization —— 那会让服务端按各自实现不同处理）：
同名 key 已有 → 复用那一行；否则**插在尾部空行之前**。
注意别写成 `rows.set(size-1, target)` 就地占用尾部空行 —— 那样会把那条空行吃掉，
表尾没有可继续录入的行了（探针先红才发现）。

### 探针
`httpsingle` 94 → **111 条**（+17）。**反向验证过两轮**：
- 退回 `contains("Bearer")` 字面判据 → 3 条红（含 Basic 污染那条）
- 去掉取值路径的规范化 → 1 条红
**失焦规范化在无头环境测不了**（`requestFocus()` 拿不到焦点，`sceneFocus` 恒 null），
所以断言全部落在纯函数 + 取值路径上。没写「失焦会补前缀」这种恒假的断言。

截图 `single-headers-token.png` / `-filled.png`：4 个按钮的工具行放得下，
右侧「常用请求头」没被挤掉。

diff 50 · sel 20 · tsui 21 · smoke 22 · image 27 全绿；jar 纯净度 0；

### 诊断：段① 还在用「表单面板」词汇
左标签（`field(...)`）+ `ComboBox` 下拉 + 收起式 `TitledPane`，
而单一请求页已是「请求编辑器」词汇：请求行 + 页签 + 分段控件 + 工具行。
两页没共用同一套编辑器组件 —— 这是根因。

### 浏览器实测抓到的两处真问题（推算不出来）
1. **预算表把「正文 232」当成了「卡片 232」** —— 漏了卡片头 38 和上下边框 2。
   真实段① = 272px → 整页 670px，**超 653 预算 17px**。
2. **请求体编辑器只能给 3 行（48px）**：最初画 4 行 76px 就是上面那个超预算的来源。
   回到 3 行后段① 244px、整页 642px，余 11px。

→ **「结构断言全绿 ≠ 长得对」**：四个子节点都在、样式也对，
但竖向账只有在浏览器里量 `getBoundingClientRect` 才暴露。

### 另一处必须内联的取舍
占位符说明**不能单起一行**（264px 会超预算），必须内联到请求行右端 ——
单一请求页本来就是这么做的（`statusBox` 与请求行同行），不是权宜之计。

### 校验器的两条硬断言（各抓到一个真缺陷，务必保留）
1. **标尺标签数字 == 该行实测高度**。尺子刻错比画布画错更危险：
   我第一版标「段① 232」而实测 244，标尺让一份错的预算看起来像已核对过。
2. **键值表列宽合计 == 容器内宽**（实测 899 = 外宽 901 − 边框 1×2）。
   差这 2px 肉眼看不出来，但列和超了会被 `overflow:hidden` 悄悄裁掉最后一列。

### 踩到的坑
- **卫生扫描会误伤 UI 元素本身**：勾选框里的 `✓` 被判成装饰符号。
  改成 CSS 画（accent 底 + `::after` 白色对勾），不写字形。
- **Chrome `--screenshot` 在中文 Windows 下要用正斜杠路径**，

## 批处理段① 改版 —— 实施完毕（设计稿已批准）

### 实施中最重要的一条教训
> **探针量高度量不到「被父容器裁掉」。**

`.batch-tabs` 高度给 110 时，TabPane 的 content-area 装不下 96 的 bodyBox，
把编辑器裁掉 —— 而 `bodyArea.getHeight()` 仍报 50px、visible=true、
skin 也建好了。**32 条断言全绿，截图上编辑器只剩一条边。**

补的断言要断「编辑器底边 vs **TabPane 的 content-area** 底边」。
**第一版断错了**（跟 `bodyTabContent` 比）—— 它自己也会被压扁，
所以在 TabPane=110 时实测仍为 true，**恒真**。恒真断言比没有断言更危险。
反向验证：154→110 转红（`编辑器完整可见 = false`）。

→ 这条要进项目约定：**任何「装得下吗」的断言都不能只量自身高度，
必须量它相对父容器可视区的位置。**

## 批处理段① 加高：让 Params/Headers 的表能输入内容

用户报「间距太小，无法输入内容」（截图里 Headers 只看得见表头那一条），
要求「调大间距 + 增加滚动条 + 行高加大到 40 + 整体都可以增加高度，段3也向下挪」。

### 根因：三个页签共享一个 TabPane 高度，而它按 Body 页签（编辑器）定
`.batch-tabs` 当时是 154 = 轨 43.33 + padding 14 + 内容 96（Body 的需求）。
切到 Headers 后表只拿到 96 − 38（工具行）− 8（间距）= **50**（表头 40 + 10），
**只看得见表头那一条**。

→ **按最高的那个页签定**（Params/Headers 要 3 行 + 滚动条）。

### 实测账
- `.batch-tabs` 154 → **277** = 轨 43.33 + padding 14 + 内容 220
  （220 = 工具行 38 + 间距 8 + 表 174；174 = 表头 40 + **3 行 × 40** + **14 滚动条**）
- 段① 252.7 → **376**；段③ 守 340；整页 **774.67 > 654** → **外层出现滚动条**（用户要的）
- 段① 收起时（导入 CSV / 执行时自动收起）段③ 回到 556 → 结果表 12 行

### 行高 40 只作用于段①
用 `.batch-kv` 作用域类（`KeyValueTable` 的 VBox 上加），**不动全站 34 的口径**。
行内常驻输入框也跟着抬到 32，否则 26px 的框浮在 40px 行里留白不匀。
**行数换算变了吗**：`(表高 − 40) ÷ 40`（表头也是 40，别再减一次）。

### 那 14px 是特意留给滚动条的
行高变大后 3 行就填满，不留这一条用户看不到「下面还有」，
会以为表就这么高。`.batch-kv .scroll-bar { -fx-opacity: 1 }` 显式开
（AtlantaFX 默认叠了不透明度）。

### 断言：作废 2 条、新增 3 条
作废（**口径随取舍变化，不是实现坏了**，务必在名字里写清）：
- 「整页正好铺满 653」→「整页允许超出视口（外层滚动兜底）」+「段③ 守 340 保底」
- 「段① 变矮后余量归段③」——段① 现在是**加高**不是变矮 →「段③ 始终守住 340」
新增：
- 「Headers 能显示 ≥ 2 行（原来 0 行）」
- 「行高 40」
- 「内容超出时竖滚动条可见」
反向验证：TabPane 277→154 时前两条转红（可见 1 行）。

### 踩坑：TableView 滚动条没有 `vertical` style class
style class 只有 `scroll-bar`，竖/横是**伪类** `:vertical`/`:horizontal` ——
`getStyleClass().contains("vertical")` **永远 false**，第一版判据因此恒假。
改用几何判方向（宽 < 20 判竖向）。

### 顺手
Body 页签标题 `Body · 无 (1 项)` → `Body · 无（有内容）`：
批处理页的请求体是**一段模板**不是「若干项」，写「1 项」会被理解成表单字段数。

## 批处理 Body：Form 类型也用键值表（用户报「格式与单一请求不一样」）

截图里红框指着分段控件的 **Form**。两层差异：
① 外观：批处理五种类型共用一个文本区，单一请求页每类型有专属编辑器
② 实质：批处理选 Form 只能手填 `a=1&b=2`（`prepareResultRows` 只把 body 文本
塞进 `spec.body`，`formFields` 从没填过 → 引擎 FORM 分支落到兼容路径）

用户选：**给 Form 也用键值表**（Content-Type 标签不动）。

### 改法
- `bodyTabContent`（StackPane）叠 `bodyArea` + `formDataTable`，
  `showBodyEditor(type)` 切 visible+managed → **各自内容不丢**
- Form 模式 `setFileRowsAllowed(false)` 隐藏「类型」列
- 内容区高度跟着换：文本区 50 / Form 表 174
- **Form 时 `spec.body` 必须置空** —— 否则键值与文本**重复发送**
- 键值按 CSV 行替换后进 `spec.formFields`，引擎 `encodeForm` 做百分号编码
- `applyBodyDegrade` 两个编辑器都要降级

### 顺带修好一个更老的缺陷：Params 的值从来没进过请求
那一页写着「这些键值会以 query 参数拼到 URL 之后」，但 `prepareResultRows`
只读了 url/headers/body 三处 —— **说明文字是假的**。现在 `appendQuery` 真拼。

### 断言踩的两个坑（都是「恒真/太松」）
