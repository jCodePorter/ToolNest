## UI 细腻度修复（用户反馈驱动）

用户给出一张 HTTP 请求工具页截图，标了三处「不够细腻」：顶部动作按钮、外层页签、
「超时」数字框。要求继续打磨细节。

### 诊断手法（可复用）

1. **像素扫描**：Python + PIL 对截图做横向 / 竖向颜色边界扫描，量出每个控件的
   真实渲染尺寸。关键数据 —— 动作按钮 **187 × 18px**、页签轨道 **195 × 47px**
   （白块 101 × 43，内边距仅 1px）、GET 下拉 **121 × 36px**、数字框 84 × 33px。
   一眼看出问题：同一垂直堆栈上是 **18px → 20px 间隙 → 47px**，毫无体系。

2. **写临时诊断探针**（`HeightProbe`，用完即删）：构造真实模块 → 放进 Scene →
   打印每个控件的 `prefHeight / minHeight / 实际高度`。一次定位根因：
   `Button pref=32.0 min=18.0 实际=18.0`。
   对照组很关键：孤立放进大 StackPane 的同一个按钮是 32px —— 说明 CSS 生效，
   问题在父容器压缩，而不是样式没应用。**排除法比读代码快得多。**

### 根因（两个层次，缺一不可）

1. **CSS 只写 `-fx-pref-height` 不写 `-fx-min-height`**。JavaFX 里 pref 只是建议值，
   父容器空间不足时一路压到 min，而 min 的默认值是内容自然高 —— 12.5px 字的按钮
   变成 18px 细条。实测 32px 按钮 → 18px、104px 键值表 → 55px。

2. **`ContentPane` 用「直接子节点有没有 `VGrow`」判断页面要不要滚动**，判据不成立。
   HTTP 页的响应区设了 `VGrow`，于是被判成「铺满一屏」不给滚动 —— 可这页需要
   1000+px，剩下 300px 的缺口就变成了对子控件的硬压。

### 修复

- **app.css**：给 `.button` / `.text-field` / `.combo-box` / `.spinner` / `.back-button` /
  `.segmented-item` / `.http-url` / `.http-method` / `.http-send` / `.chip` 全部补
  `-fx-min-height`；确立**控件高度阶梯 32 / 36 / 30 / 28 四档**。
- **app.css**：外层胶囊页签由「padding 撑高（实测滑块 42px、轨道 48px）」改为
  固定 32px（轨道 38px），与按钮同处一个高度带。
- **app.css**：数字框收成一个整体 —— 原来「输入框 + 独立箭头区」两块拼接、
  边框与圆角各画各的，和同屏下拉框明显不是一套东西。
- **app.css**：滚动条显式 `-fx-opacity: 1` + 定宽 11px + 令牌加深。实测原 thumb
  渲染成 `#e0e4e9`，与内容底 `#f8f9fb` 无法分辨。
- **`ContentPane`**：删掉 `isFillLayout` 分流，统一 `ScrollPane` +
  `minHeight = USE_PREF_SIZE`。机制见下方「核心机制」。
- **`HttpToolModule`**：动作按钮图标由 Unicode `↑` 改为 `Icons.of("arrow-right")`；
  删掉与请求行重复的 `{列名}` 占位符说明。
- 中文括号统一：纯中文用全角（），含英文 / 数字用半角并前置空格。

### 验证

- **254 条断言全绿**（250 + 4 新增）；CSS 解析错误 0；产物纯净度 0。
- 新增 4 条「尺寸完整性」断言（落在 `nav` 探针）：HTTP 页内每个按钮 / 输入框 /
  下拉 / 数字框的实际高度 ≥ 首选高度；整页内容按首选高度布局。
- **两条都做了反向验证**：撤掉 CSS `min-height` → 前一条变红并精确点名 3 个被压控件；
  撤掉 `ContentPane` 的最小高度 → 后一条变红（内容高 1054px → 596px）。
- 重新打包 `build\dist\ToolNest\ToolNest.exe`（10:53）。

### 教训

- **用户运行的 exe 可能落后于源码**。这次对比发现用户截图里的文案与当前源码不一致
  （`build/dist` 打包于 17:42，而 app.css 改到 19:10）。改完样式必须重新打包，

## 2026-09-28 下午 · 架构分层重构（core / ui / app / features）

**需求**：用户认为「UI 层与业务逻辑层搅和在一块」，要求按业务分包 + UI / 业务 / 数据分层 +
薄数据层并入业务层 + 建立公共 UI 组件层。四项决策点用户均选了推荐的根治方案。

**诊断（七项实证，详见 `ARCHITECTURE.md`）**：核心病因是 `ToolModule` 一个接口同时承担
元数据契约 / 界面工厂 / 业务入口三个角色，所有模块都被它带着往下混。

**已完成的改动**

   **`Launcher` 与 pom / package.cmd 的 main.class 无需改动**（这是刻意的选择）
3. **ui 三分子包**（ADR-005）：`ui/shell`（框架，不可复用）/ `ui/components`（公共组件）/ `ui/spi`；
   `KeyValueTable` 从 `features/http` 迁入 `ui/components`
4. **业务分包**（ADR-003）：`modules/` → `features/`，`modules/file` → `features/filehash`
5. **17 个 `package-info.java`**：把分层约定编码进代码，随代码演进
6. **删死代码**：10 个模块的 `icon()`（零调用）、`UiKit.segmented()`（零调用）、
   `UiKit.BODY_PADDING`（声明未用）
7. **探针同步**：10 个探针文件 + `verify.cmd` 类名映射表

**踩到的三个坑（都很隐蔽）**

- **package 声明不能用带点的规则替换**：`package ...modules.file;` 结尾是**分号**，
  而 import 是 `modules.file.XxxHashOps`（带点）。按 `.` 写规则会漏掉 package 行，
  把 `filehash` 包错写成 `file` → 报「类重复: features.file.FileHashModule」。
  **教训：批量改包名时 package 声明行要单独处理**
- **同包可见性陷阱**：`ui/shell` 的类与 `UiKit`/`Icons` 原本同在 `ui` 包，直接调用**没有 import 语句**；
  分包后必须主动补 import，否则「无从下手改」。`KeyValueTable` 迁出后
  `BatchPanel`/`SingleRequestPanel` 对它的同包引用同理
- **前缀重叠**：`ui.ContentPane` 与探针名 `ui.ContentPaneProbe` 前缀相同，
  替换包名必须用**词边界** `\b`，否则会把探针类名改成 `ui.shell.ContentPaneProbe`

**验证**：231 条通过。完整基线 275 = 231 + tsui 的 4 条剪贴板断言 + qrpic 40 条。
后两者失败/未跑**均因系统剪贴板被独占**，已用不含项目代码的最小程序复现

### 算法：三段式，缺一不成三态

1. **行级 LCS**（DP，`short` 表，`DP_CELL_LIMIT = 4M`）求出原地不动的最长公共子序列，
   块间是 SAME，块内是待分类的「删除组 + 新增组」。
2. **块内单调最优配对**（相似度 DP，`MATCH_CELL_LIMIT = 40k`，`SIMILARITY_THRESHOLD = 0.5`）
   判定「修改」。**这是最容易写错的一步**（见下）。
3. **行内 token LCS**（`Granularity.WORD` 用 `[A-Za-z0-9_]+|\s+|.` 切词，`CHAR` 逐字符，
   `SPAN_CELL_LIMIT = 1M`）标出行内增删片段。

### 真实缺陷一：「块内按位置逐对比较」会把修改拆成一删一增

第一版在错位块里按位置配对：`db_pool = 10` 去配 `worker = 8`，相似度低于阈值 →
判成「删 db_pool + 加 worker」，统计变成 `+3 / ~5 / −2`、组数 5。

修法：**单调最优配对** —— 只允许相似度 ≥ 阈值的配对，用 DP 求「总相似度最大且下标单调」
的配对集合，再回溯出 `pairOfDel[] / pairOfAdd[]`；遍历时左行若已配对就走 MOD，
未配对走 DEL，右行未配对走 ADD。跨越一个删除行的修改由此能被认出来。

> 教训：**「按位置配对」在块内已经错位的前提下必然错**。只要块内删除数与新增数不等，
> 位置就失去意义；必须用相似度矩阵 + 单调约束。

### 真实缺陷二（最隐蔽）：样式类名多拼一层前缀，CSS 选择器全部落空

```java
// 错的
bar.getStyleClass().addAll("diff-seg", "diff-seg-" + kindClass(g.kind()));
// kindClass 已经返回 "diff-mod"，于是类名是 "diff-seg-diff-mod"
// 而 CSS 写的是 .diff-seg.diff-mod  → 不匹配
```

症状极具欺骗性：**节点存在、`managed=true`、`visible=true`、`getWidth()/getHeight()` 全部正常**，
只是 `-fx-background-color` 没应用 → 填充透明。变更密度图上除当前组（那条有 `diff-seg-cur`
的 `-fx-border-color` 兜底）外**四条色条全看不见**；清单里的类型标签同样没有色底。

**为什么探针没抓到**：断言写的是 `count(content, "diff-seg") == 4` —— 数的是节点数。

**修法（两件一起做）**

1. 复用语义类：`addAll("diff-seg", kindClass(g.kind()))` —— 截图中立项，一行修两处。
2. **加渲染级断言**（这才是根因治理）：

```java
private static String fillOf(Region region) {
    Background bg = region.getBackground();
    if (bg == null || bg.getFills().isEmpty()) return "<无>";
    Paint p = bg.getFills().get(0).getFill();
    if (p instanceof Color c) {
        return String.format("#%02x%02x%02x",
                (int) Math.round(c.getRed() * 255),   // ← 0.0–1.0，必须乘 255
                (int) Math.round(c.getGreen() * 255),
                (int) Math.round(c.getBlue() * 255));
    }
    return p.toString();
}
```

断言「4 条都真的上了色 + 颜色与类型对得上」，把「节点存在」与「节点真的有效」分开。

> 反向验证：把两处样式类改回带前缀的写法 → **3 条断言变红**，详情是
> `[<无>, <无>, <无>, <无>]`，一眼看出是「没上色」而不是「没节点」。
> 这一条值得推广：**凡是靠样式类决定外观的地方，都要断言到渲染色**。

### 真实缺陷三：`rowGroup` 默认 0 = 「第 0 组」的合法下标

`new int[rows]` 默认全 0，而 0 是有效组号 → 所有普通行都被当成「当前组」，38 行带上高亮。
修法：`Arrays.fill(rowGroup, -1)`，并且遍历时加 `currentGroup >= 0` 守卫
（否则「无差异」时的 `-1` 会与 `rowGroup` 的 `-1` 撞上，把普通行误染）。

### 真实缺陷四：面板双态只初始化了一侧

`TextArea` 无法行级染色，所以每侧是「编辑态 `TextArea` / 对比态 `ScrollPane`+行 `VBox`」两个视图
切 `visible/managed`。`setEditing` 只对左栏调了一次 → 右栏两个视图同时可见、叠在一起。
修法：两侧都初始化，并加「两侧第一次都有内容时自动进入对比态」（`bothFilled` 标志），
否则用户填完还得再点一次。

### 其他实现要点

- **行高 20px 三件套**（min/pref/max）必须一起写，否则空间不足时被压成细条。
- **`region()` 刻意压低首选高度**（min 220 / pref 260）：详情页统一装在 `ScrollPane` 里，
  模块根节点的「首选高度」决定页面高度 —— 不压低的话三列会按内容高度把整页撑出外层滚动条，
  而滚动应该留在栏内。
- **面板 `setClip(Rectangle arc 16)`**：行底会盖掉 8px 圆角。
- **变更密度图**：轨道 108px，条 `layoutY = rowFrom / total * 108`，条长
  `track.width * min(1, rowCount / maxGroupRows)`。
- **刻度用零高度容器包 Label**：直接摆 `Label` 会因它自带约 14px 高度让首尾各缩半行
  （表现为轨道左缘竖线在末端多出一截悬空尾巴）。`StackPane` + `min/pref/maxHeight = 0`
  + `Pos.CENTER_LEFT`，容器刻意**不加样式类**（高度不能被 CSS 覆盖）。
- **清单条目用 `VBox` + `setOnMouseClicked`**，不用 `Button` + graphic：graphic 不会被拉伸，
  宽度只能手工算，反而更脆。
- **`.diff-item-tag` / `.diff-seg` 的规则都写成组合选择器**（`.diff-seg.diff-mod`），
  避免与行的 `.diff-row.diff-mod` 互相干扰 —— 但也正因如此才对类名拼写更敏感（见缺陷二）。

## 第二轮：修「只贴一侧」时的样式错乱

用户反馈：「贴入原文后，样式错乱」（附真实运行截图，只往左栏贴了内容、右栏为空）。
一次截图里其实叠了**三个互相独立**的缺陷，全都只在「两侧内容不对称」时才显形。

### 缺陷一：空态文案左贴边、右端溢出（用户看到的「错乱」）

- 现象：中列空态的图标水平居中，但主文案与次文案**整块贴在左边缘**，视觉轴不齐。
- 诊断：`Label` 的 `maxWidth` 默认 `USE_PREF_SIZE`（按文字原宽摆放，不随容器伸缩），
  且文字块默认 `-fx-alignment: CENTER_LEFT` → 贴左。
- 修法三件套：
  1. `UiKit.emptyState` 里两个标签都 `setMaxWidth(Double.MAX_VALUE)`（撑满容器宽）；
  2. CSS **同时**补 `-fx-alignment: center` 与 `-fx-text-alignment: center`；
  3. `.diff-band .empty-state { -fx-padding: 26 14 }` 收窄窄栏留白，文案按「一行约 14 个汉字」
     自己写死换行点。
- **中途踩的坑**：第一版断言查 `hint.getTextAlignment()`（=`-fx-text-alignment`），它**确实是 CENTER**，
  断言绿着但画面仍贴左 —— 真正决定块位置的是 `-fx-alignment`。
  → 断言改为量 `label.lookup(".text")` 的中心与容器中心比对后才有效。

### 缺陷二：中列随内容横向跳 50px（同一次测量里顺带暴露）

- 现象：中列（差异栏）x 坐标在 517 / 573 / 523 之间跳 —— 取决于哪一侧内容更宽。
- 根因：左右面板的 minWidth/prefWidth 默认由内容决定；长 URL 把那一栏撑宽，HBox 重新分配。
- **第一次修复只写 `setMinWidth(0)` → 仍然不等宽**（左 530 / 右 430）。
  因为 `HBox` 是按「各子节点**首选宽** + 均摊剩余」分配的。
- 最终修法：新增 `PANE_PREF_WIDTH = 320`，`setMinWidth(0)` **与** `setPrefWidth(...)` 两处都拉齐。
  四个状态下中列恒为 523..742。

### 缺陷三：只填一侧却渲染出「整栏删除 + 差异 1 处」

- 现象：只填左栏时左栏 22 行全被染成 `diff-del` 粉色，底部写「差异 1 处」，「下一处」可用。
  算法上没错（另一侧确实全没了），但**表意上毫无意义** —— 用户还没输入完，任何差异数字都只会误导。
- 修法：新增 `readyToCompare()`（`!text(left).isEmpty() && !text(right).isEmpty()`）
  作为**差异结论的唯一出口开关**，四个出口共用：
  ① 行级高亮（不 ready 就退回编辑态）② 中列统计 ③ 底部数字 ④ 跳转/复制按钮置灰。
  另外让「可比对」这个条件翻转时自动切模式（刚贴完两份就自动进对比态，退化成单侧就自动回编辑态），
  只在条件本身翻转时才动模式，所以用户手动切的模式不会被反复抢走。

### 诊断手法：扫描边框像素自动定位栏边界

第一版按坐标猜栏位置（假设 535..700，实际 573..792）→ 裁剪图全是错的，白白绕了一圈。
改用「扫描中灰色边框像素自动定位三栏边界」后一次看清。
**按坐标猜视觉元素的位置是效率陷阱，让程序自己找边界。**
